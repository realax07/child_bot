# Контракт артефактов между сабагентами конвейера

> Обязательный документ. Определяет интерфейсы передачи работы между этапами. Сабагент вправе принять артефакт только при выполнении условий входа и обязан отдать артефакт, удовлетворяющий условиям выхода.

## Общие правила

1. Передача работы — **только через файлы в репозитории проекта**, не через контекст диалога.
2. Каждая роль проверяет входной артефакт по чеклисту «Условия входа». Несоответствие — эскалация проектному менеджеру, не «доделывание за предыдущего».
3. Выходной артефакт должен проходить чеклист самовалидации агента-автора (см. инструкцию агента).
4. Форматы фиксированы; изменение формата — изменение настоящего контракта через коммит и согласование.

## Диаграмма потока

```
Заказчик ⇄ [ba_agent] → requirements.md → [sa_agent] → openspec/* + sdd.md
                                                              │
        [qa_automation] ← approved/* ← [qa_case_reviewer] ⇄ new/* ← [qa_case_author] ← спека (openspec/*)
```

> **remove-qa-checklist (матрица Заказчика 2026-10-12):** этап «QA-аналитик
> чеклистов» (qa_checklist, артефакт CHK-чеклиста) упразднен. Автор кейсов
> читает спеку напрямую; трассировка — TC → `### Requirement:`/`#### Scenario:`
> спеки. Существующие чеклисты в `test-model/checklists/` — append-only
> история: не удаляются, новые не пишутся и не проверяются (flow_check/pr_validate).

## Контракт 3: Системный аналитик → QA (спека как источник кейсов, `openspec/`)

| Поле | Значение |
|---|---|
| Производитель | `sa_agent` (выход контракта 2) |
| Потребитель | `qa_case_author_agent` (ранее — упраздненный `qa_checklist_agent`) |

**Условия входа:** те же, что в контракте 2 (покрытие Must-требований, сценарии GIVEN/WHEN/THEN, отсутствие реализации в specs). Дополнительно: спека доступна для чтения, change-id проставлен.

## Контракт 4: Спека → QA автор кейсов (`openspec/` → `test-model/new/`)

| Поле | Значение |
|---|---|
| Производитель | `sa_agent` (дельты/спека) |
| Потребитель | `qa_case_author_agent` |
| Путь | `test-model/new/<change-id>/TC-<domain>-NNN.md` |

**Условия входа (напрямую по спеке, без чеклиста):**
- [ ] Каждый Scenario спеки рассмотрен как кандидат в кейсы (покрытие сценариев)
- [ ] Для требований с валидацией есть негативные/граничные кейсы
- [ ] Каждый кейс имеет источник: `### Requirement:`/`#### Scenario:` спеки + FR-N/NFR-N
- [ ] Найденные дефекты спеки эскалированы (не «доделаны за СА»)

## Контракт 5: Автор ⇄ Ревьюер (`test-model/new/` ↔ `test-model/reviews/`)

| Поле | Значение |
|---|---|
| Производитель | `qa_case_author_agent` |
| Потребитель | `qa_case_reviewer_agent` (и обратно на доработку) |
| Пути | кейсы: `test-model/new/<change-id>/TC-<domain>-NNN.md` — **один файл на кейс, имя файла = ID кейса** (H1); ревью: `test-model/reviews/<change-id>/review-NNN.md` |

**Цикл:** автор кладет кейсы в `new/` → ревьюер пишет вердикт в `reviews/` → «вернуть» = автор исправляет и обновляет файлы в `new/` → повторное ревью (следующая итерация NNN) → «одобрить» = ревьюер переносит кейсы в `test-model/approved/<change-id>/`.

**Партионное ревью (H3, при >12 файлов кейсов).** Если в `new/<change-id>/` больше 12 файлов кейсов, ПМ делит пакет на партии ≤12 файлов (алфавитный порядок имен — детерминированно, без отбора) и запускает ревью партиями **последовательно** (зона `reviews/` общая, параллель — риск коллизии нумерации):

- в goal делегации ПМ передает явный список файлов партии; ревьюер работает только с ним;
- каждая партия = своя итерация `review-NNN.md` с вердиктом по партии; нумерация NNN — сквозная по пакету (следующий свободный номер);
- «одобрить» партии = ревьюер переносит в `approved/<change-id>/` **только файлы этой партии** (частичный перенос легален);
- «вернуть» партии = автор дорабатывает только файлы партии; остальные партии не блокируются;
- пакет одобрен, когда последняя итерация каждой партии — «одобрить» и `new/<change-id>/` пуст.

**Условия входа ревью (проверяет ревьюер):**
- [ ] Каждый кейс трассирован к спеке (Requirement/Scenario), сценарии спеки покрыты
- [ ] Один файл = один кейс, имя файла = ID кейса (H1; дублируется проверкой flow_check)
- [ ] Каждый кейс: предусловия, атомарные шаги, проверяемый результат, конкретные данные
- [ ] Негативные кейсы ожидают явную ошибку
- [ ] Ожидаемые результаты не противоречат Scenario спеки

**Условия выхода ревью:** вердикт «одобрить» только при отсутствии blocker/major замечаний.

## Контракт 6: Ревьюер → Автоматизатор (`test-model/approved/`)

| Поле | Значение |
|---|---|
| Производитель | `qa_case_reviewer_agent` (переносом в approved/) |
| Потребитель | `qa_automation_agent` |

**Условия входа:**
- [ ] Кейсы лежат в `test-model/approved/<change-id>/` (наличие в `new/` = работа не начата)
- [ ] Кейсы прошли ревью (существует review-файл с вердиктом «одобрить»)
- [ ] Для API-кейсов: контракты в `sdd.md` достаточны для формирования запросов
- [ ] Для web-кейсов: известны UI-локаторы или сценарии навигации воспроизводимы

**Условия выхода автоматизатора:** тесты покрывают все одобренные кейсы, трассировка кейс → тест заполнена, прогон выполнен, падения оформлены баг-репортами в `test-model/bugs/`.

## Контракт 1: Заказчик → БА → Системный аналитик (`requirements.md`)

| Поле | Значение |
|---|---|
| Производитель | `ba_agent` (при участии Заказчика) |
| Потребитель | `sa_agent` |
| Путь | `requirements.md` в корне репозитория проекта |

**Условия входа (проверяет системный аналитик):**
- [ ] Первая строка файла — преамбула ответственности: `> Статус: <ЧЕРНОВИК rN | ГОТОВ К УТВЕРЖДЕНИЮ rN | УТВЕРЖДЕН rN> | Автор: ba_agent | История: r1 → … → rN (кто и когда сменил статус)`
- [ ] Присутствуют все 7 разделов структуры ТЗ (описание, аудитория, FR, NFR, приоритеты MoSCoW, ограничения, открытые вопросы)
- [ ] Каждое FR/NFR имеет уникальный идентификатор (`FR-N`, `NFR-N`)
- [ ] Раздел «Приоритеты» заполнен; требования без приоритета отсутствуют
- [ ] Нет оценочных формулировок без критерия («быстро», «удобно»)
- [ ] Открытые вопросы либо закрыты Заказчиком, либо явно помечены и не блокируют FR с приоритетом Must

**Уровни решений по эскалациям (decision rights):**

| Тип | Кто решает | Фиксация | Арбитраж спекой |
|---|---|---|---|
| Спеки/поведение продукта | Заказчик | дословная цитата в `answers_roundN.md` | — (сам источник) |
| Делегированное Заказчиком | ПМ | пометка **«интерпретация ПМ»** в ТЗ задачи с основанием (ОВ-N / ретро-решение) | НЕ отменяет приоритет спеки: при противоречии — обычная эскалация |
| Технические детали в границах спеки | Исполнитель (dev/QA) | в докоммитном сообщении/отчете | ревьюер проверяет границы |

Правила: (1) делегированное решение никогда не переписывает спеку — ПМ не законодатель требований; (2) у делегирования есть предел: финансы/сроки/смена приоритетов MoSCoW/изменение Must-требований — всегда обратно Заказчику; (3) при сомнении, к какому типу отнести, — тип «Заказчик».

**Статусная модель requirements.md (переходы):**

| Статус | Кто переводит | Условие перехода |
|---|---|---|
| ЧЕРНОВИК rN | БА | любые правки; вопросный раунд идет |
| ГОТОВ К УТВЕРЖДЕНИЮ rN | БА | все ОВ текущего раунда закрыты, Must-требования согласованы |
| УТВЕРЖДЕН rN | **только Заказчик (через ПМ)** | явное «подтверждаю» Заказчика |

Правила: (1) УТВЕРЖДЕН — условие входа контракта 2 (СА не стартует по неутвержденному ТЗ; исключение — работа по черновику по прямому указанию Заказчика, фиксируется в answers/ТЗ); (2) смена статуса отражается в преамбуле (История, append-only — правило 7 AGENTS.md); (3) переоткрытие утвержденного ТЗ = новая правка rN+1 с прохождением цикла заново.

**Обязательный артефакт раунда вопросов — `docs/ba/answers_roundN.md`:** пишется БА в момент получения ответов Заказчика (не по памяти после), содержит: дату, дословные цитаты ответов, связь ОВ-N → изменение в `requirements.md` (или «без изменений — уточнение»). Раунд считается завершенным только при существующем answers-файле; требования rN+1 без answers_roundN.md валидны только если раунд не задавал вопросов (это фиксируется в файле записью «вопросов в раунде N не было»).

**При нарушении:** системный аналитик возвращает ТЗ проектному менеджеру со списком дефектов. Не интерпретирует требования за БА.

## Контракт 2: Системный аналитик → Разработка (OpenSpec + SDD)

| Поле | Значение |
|---|---|
| Производитель | `sa_agent` |
| Потребитель | агент-разработчик (будущая роль) |
| Пути | `openspec/` в репозитории проекта + `sdd.md` в корне |

**Структура выхода:**
```
openspec/
├── specs/                  # источник правды: поведение системы по доменам
│   └── <domain>/spec.md    # Requirement + Scenario (GIVEN/WHEN/THEN)
└── changes/
    └── <change-id>/        # пакет изменений
        ├── proposal.md     # зачем и что (intent, scope, approach)
        ├── specs/          # дельты: ADDED / MODIFIED / REMOVED
        ├── research.md     # проработка альтернатив до design (E12-заимствование)
        ├── design.md       # как: техрешения, архитектура
        └── tasks.md        # чеклист реализации; [P] = задачи, независимые друг от друга (можно параллелить)
sdd.md                      # системный дизайн: стек, компоненты, контракты API, данные
```

**Условия входа (проверяет разработчик / валидатор):**
- [ ] ТЗ имеет статус УТВЕРЖДЕН (статусная модель контракта 1); для версии rN существуют `docs/ba/answers_round*.md` всех раундов вопросов этой версии (контракт 1, «Обязательный артефакт раунда»)
- [ ] Каждое Must-требование из `requirements.md` покрыто Requirement в spec или дельте (трассировка FR-N → Requirement)
- [ ] Каждое Requirement имеет хотя бы один тестируемый Scenario в формате GIVEN/WHEN/THEN
- [ ] Модальность по RFC 2119 (MUST/SHALL/SHOULD/MAY) использована осознанно
- [ ] В spec.md отсутствует реализация (имена классов, библиотеки, шаги кода) — только наблюдаемое поведение
- [ ] `tasks.md` покрывает все дельты; задачи атомарны (одна сессия = одна задача); независимые задачи помечены `[P]` (параллелизация по правилу 11 AGENTS.md — worktree на сессию)
- [ ] `research.md` фиксирует рассмотренные альтернативы ключевых техрешений и почему выбранное решение лучше (кратко; для тривиальных инкрементов — строка «альтернативы не рассматривались, инкремент тривиален»)
- [ ] `sdd.md` фиксирует: стек, компоненты, контракты API, модель данных, решения по НФТ
- [ ] Открытые вопросы ТЗ либо закрыты, либо отражены в proposal.md (Out of scope / допущения)

**При нарушении:** разработчик возвращает пакет проектному менеджеру со списком дефектов.

## Контракт 7: Реализация → Архивация в master-spec (`openspec/specs/`)

Master-spec — структурированное описание функционала **as is** на текущий момент: `openspec/specs/<domain>/spec.md`. Change-пакет — только предложение; пока дельты не влиты в specs/, master-spec не соответствует реальности. Архивация — обязательная фаза завершения change, а не опция.

| Поле | Значение |
|---|---|
| Производитель | агент-интегратор (архивация) по факту завершения реализации |
| Потребитель | все последующие роли (СА, QA — работают уже от обновленного as is) |
| Пути | `openspec/changes/<change-id>/` → слитo в `openspec/specs/`, пакет переносится в `openspec/changes/archive/<дата>-<change-id>/` |

**Триггер архивации (все три обязательны):**
- [ ] Все задачи tasks.md отмечены `[x]`
- [ ] QA-контур этапа завершен: автотесты написаны, прогон зеленый (или падения оформлены баг-репортами и приняты Заказчиком)
- [ ] Явное разрешение проектного менеджера (после отчета исполнителя)

**Процедура (механика):**
1. Дельты change-пакета сливаются в master-spec: `ADDED Requirements` — appended, `MODIFIED` — замещают существующие Requirement (целиком, с обновлением сценариев), `REMOVED` — удаляются. Механика: `openspec archive <change-id>` (CLI), при конфликте — вручную по этому правилу.
2. Новый/измененный spec валидируется: `openspec validate --all --strict`.
3. Пакет переносится в `openspec/changes/archive/<дата>-<change-id>/` — история сохраняется (rule 7, append-only).
4. `flow_check.py` — зеленый.

**Условия выхода (проверяет оркестратор):**
- [ ] Каждый Requirement из дельт присутствует в `openspec/specs/` (ADDED/MODIFIED — там, REMOVED — отсутствует)
- [ ] Валидация strict зеленая; в master-spec нет дублей Requirement с одинаковым названием в одном домене
- [ ] Пакет в `changes/archive/`, в активных `changes/` его нет
- [ ] `sdd.md` обновлен, если дельты меняли API-контракты или модель данных

**При нарушении:** архивация не засчитана; следующий change, читающий as is по устаревшему master-spec, получает право на возврат всей цепочки.

**Запрещено:** архивировать при незакрытых задачах или красном QA; править master-spec напрямую мимо change-пакета (эволюция as is только через дельты — иначе теряется аудит «почему изменилось»); удалять архив.

## Трассировка

Матрица трассировки FR/NFR → Requirement ведется в `sdd.md` (раздел «Трассировка»). Правило полноты: нет Requirement без источника в ТЗ; нет Must-требования без Requirement.
