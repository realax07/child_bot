# Research: add-settings-history — конспект источников и допущения

- **Дата:** 2026-11-01
- **Автор:** СА (зафиксировано ДО выбора решений design.md)

## Настройки (ТЗ §5, §5.1, §8.3, §9.3–9.4)

- §5: 12 параметров с дефолтами, хранение на каждого пользователя (settings, ключ user_id); часовой пояс — из TG-профиля при первом запуске.
- §5.1: все изменения параметров сохраняются в `settings_history`: кто (user_id), что (key), старое значение, новое значение, когда.
- §8.3 (детализация): user_id, key, old_value, new_value, changed_at — «позволит откатить настройки, посмотреть историю, отладить поведение» (откат — вне скоупа, см. proposal).
- §9.4 схема settings_history: id INTEGER PK, user_id FK, key TEXT, old_value TEXT, new_value TEXT, changed_at DATETIME.
- §7.16–7.19: главный экран (4 группы: «Режим дня», «Ночной сон», «Бодрствование», «Прочее»), запрос нового значения с форматом `5:20`/`5ч20м`, успех «старое → новое», ошибка «Не могу разобрать значение».

## settings_history — состояние схемы (проверено по main)

- PLAN-add-settings-history.md: «settings_history-таблица уже в схеме пакета 1 — используется, миграций нет».
- ФАКТИЧЕСКИ по main (src/db.py, задача 1.2): схема v1 создаёт только users / sleep_events / settings; комментарий db.py прямо говорит «settings_history и daily_summary НЕ создаются (пакеты 2–3)». CREATE TABLE settings_history в src/ нигде нет, таблица не используется.
- Следствие для design: `CREATE TABLE IF NOT EXISTS settings_history` (§9.4) добавляется в _SCHEMA_STATEMENTS db.py — идемпотентное создание при init_db, данных не лифтуем (таблица пустая) → **отдельной миграции данных нет**, anti-scope соблюдается. Расхождение PLAN↔код отмечено в report-create-change.md для ПМ.

## История (ТЗ §4.8, §7.20–7.22, PB-5)

- §4.8: сводка за сегодня; сводка за последние 7 дней; сравнение фактического бодрствования с целевым диапазоном.
- §7.20: 7 строк «ДД.ММ (дн): бодрствование H ч M мин, сон HH:MM–HH:MM, ночь HH:MM ✓/⚠️» — новые → старые; пример ⚠️ на дне с ночным уходом 22:40 (> крайнего 22:30).
- §7.21: «Я не знаю, когда ребёнок проснулся сегодня…» — пустой сегодня; §7.22: «данные за сегодня неполные — последнее событие было в 07:15».
- PB-5 (бэклог, приоритет высокий, приёмка 26.10 «нет никакой истории»): список записей за сегодня/3 дня, что засчитано сном/бодрствованием. PLAN фиксирует форму: сводка за 7 дней + за сегодня, ✓/⚠️ по границам.
- Кнопка «📊 История за неделю» — в меню §6 обоих состояний (сейчас в src/services/state.py кнопок истории/настроек НЕТ: build_menu = [событие, «↩️ Отменить последнее»]; «⏰ Подсказка сейчас» добавлена пакетом 2). callback `history:week` (§10.3), команда /history (§10.2).

## Trade-offs / допущения

- **13-й параметр на экране:** показываем target_nap_duration в «Прочее» — иначе настройка недостижима через UI, а FR-46 («каждое изменение») теряет смысл для живого ключа; §7.16 написан до решения №1. Допущение ПМ (design D21), экран структурно остаётся §7.16.
- **Период истории:** «последние 7 дней» = 7 завершённых страниц дня (граница day_start) + отдельно блок «сегодня» (PLAN); страница дня и ночные отрезки через полночь — правила D8 пакета 1, в истории не переизобретаются.
- **Строка «ночь HH:MM»** в §7.20 — время ухода в ночь (отбой) дня; для дня без отбоя строка ночи опускается (строка только при наличии факта — принцип PB-3).
- **delete_all удаляет строку users** — самая полная трактовка «ВСЁ пользователя» (PLAN); FK-каскад не используется (SQLite foreign_keys в схеме без ON DELETE), удаление — явными DELETE по user_id в одной транзакции.
- **Пресеты «Сейчас»** — дублирует кнопку «🕐 Сейчас» §7.10; вопрос закрыт: пресеты ОТМЕНЕНЫ продактом 01.11 (ОВ-5.2), в диалоге остаётся только «Сейчас».
