# Декомпозиция релизного хвоста: лимиты ручной работы ПМ (урок 2026-10-07)

## Что случилось

Релизный хвост r8-polish ПМ тянул руками в основной сессии: бамп static_v,
подъем стенда, прогоны сьютов, чистка БД, диагностика web-фейлов. Диагностика
двух стабильных фейлов утащила сессию в 3-й уровень (DOM-интроспекция Playwright
в браузере) — Заказчик: «заигрался». Это и есть граница.

## Что ПМ делает руками (легитимно)

1. Релизный однострочный хвост: бамп static_v, версии, маркеры — ветка → PR → merge.
2. Подъем/гашение стенда из main (worktree /tmp/qa-r8/wt, stand-скрипт).
3. Контрольные прогоны сьютов с полным env (web-regress-protocol) — КАК ФАКТ для доклада.
4. Квалификация красноты: env-протокол → чистота БД → продукт. ОДНА итерация каждой.

## Граница: дальше — сабагенту через конвейер

- **Правило 2 итераций**: диагноз фейла в основной сессии — максимум 2 итерации
  (гипотеза → проверка). Не подтвердилась — фикс-задача в конвейер (Флоу 2,
  BUG-NNN) сабагенту с ТЗ, содержащим уже собранные факты (симптом, стенд, что
  исключено). ПМ не делает DOM-интроспекцию, коммит-археологию и мутационные
  проверки — это работа dev/QA-агентов, и у нее нет дна.
- **Чистка БД стенда — скриптом** (db_reset.sh), не ручным sqlite: ручные DELETE
  по таблицам зациклили сессию (task_tags/gallery_tags/tag_id — schema-ползание).
- **Прогон сюиты длиннее ~6 мин — только terminal background + process wait**, не
  foreground (ограничение 600с) и не циклы sleep-poll.
- Изолированные worktree-проверки («а на старом коммите этот тест зеленый?») —
  тоже фактор в правило 2 итераций: bisect руками = диагноз, а не приемка.

## Шаблон передачи в конвейер (что зафиксировать)

BUG-NNN: симптом, репро-команда с полным env, что уже исключено (env/чистота БД),
стенд (пути, порты), подозрение с фактом (коммит/дифф), критерий закрытия
(тест зеленый + мутационная проверка). Заказчику — строка в докладе: «2 стабильных
фейла → BUG-NNN/BUG-NNM, ушли в Флоу 2», не молчание.

## CPU-лимит стенда (урок 2026-10-07 вечер)

Хост 2 vCPU / 3.9GB RAM / без swap. Прогон web-сьютов = pytest + node(playwright)
+ до 8 chrome-headless ≈ 100% CPU; load 5-7 при 2 ядрах — на этом фоне сессии
«дохнут» (stall → dropped), тесты флейтят по таймаутам. Правила:
- Осиротевшие uvicorn QA-стендов гасить после каждого релизного цикла (ps + grep
  uvicorn, возраст > 1ч без активной сессии). У портов 8377/8378/8379 host-network
  живут ПРОДА-контейнеры uid 10001 — их не трогать (kill даст Operation not
  permitted — это не баг, а признак контейнера).
- dockerd/containerd без контейнеров ели 45% CPU 4 суток — фон, требующий root;
  вопрос Заказчику, ПМ сам не рестартит.
- Доступный ПМ рычаг: renice +10 своим uvicorn-стендам во время прогонов сабагента.
- Сабагентам в ТЗ на прогоны: пачки тестов дробить (по файлу, не весь каталог),
  длинные — terminal background, иначе CPU-истощение роняет и сабагента, и стенд.

## Маркеры PR и закрытие design-сессий (урок P14)

- Валидные маркеры pr_validate: [BUG-NNN]/[change-id]/[chore]/[docs]/[ops]. [design] НЕ валиден — мокапы идут под [docs] (прецедент PR #44/#45/#104). Промежуточные dev-PR волны тоже не несут change-маркер бесконтрольно: change-маркер триггерит полный QA-хвост (impact/чеклист/approved/reviews) — он появляется только к волне QA; промежуточные — [docs]-координационные, финальный PR пакета — change-маркер.
- design_validation НЕ забывать: после код-ревью самых видимых волн (прецедент P12: review-004-design после модалки 2.x до QA), финальная сверка всех мокапов в QA-волне 5.1 (review-NNN-design.md, зона test-model/reviews/). Этап design_validation в STAGE_TABLE, роль design_validator, артефакт test-model/reviews/<change>/review-NNN-design.md.
- finish design/dev-сессии требует pm_bounds_check с ЯВНЫМ --pm-mode (sessions + --pm-registry). Забыл — сессия blocked; повторный finish игнорирует флаги, спасает --pm-resume (только для blocked по gate ERROR без дефектов по существу) → verdict returned; затем ПМ закрывает lifecycle в реестре вручную (finished → completed с evidence).

## Подготовка нового пакета flowctl (урок P14, 2026-10-08)

- ВСЕГДА сначала `--dry-run`: все DENY видны за один прогон — не проводи боевые попытки (4 DENY подряд = тот самый «заигрался»).
- Decision-record (P0.4): action в файле должен ТОЧНО совпадать с действием этапа (start_flow1 ≠ create_change); поле commit обязательно; scope.project = значению --project (для ekotov-wiki это `wiki`, НЕ ekotov-wiki-par).
- --path: каталог с `**` после change-id не матчится политикой; передавай конкретные файлы (proposal.md, requirements.md, research.md, design.md, tasks.md) плюс литеральное `openspec/changes/<id>/specs/**` — литеральное совпадение принимается.
- PR создания пакета — маркер `[docs]` (прецедент PR #42); change-маркер триггерит полный QA-хвост pr_validate, появляющийся только в финальном PR пакета. gh pr edit может падать (GraphQL Projects-classic) — тогда close + новый PR с того же head.
- --create-worktree требует scripts/session_worktree.sh (лежит в ai-factory, в ekotov-wiki нет) — работай веткой в основном репо.
