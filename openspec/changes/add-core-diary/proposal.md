# Proposal: add-core-diary — ядро дневника сна (Пакет 1)

- **Флоу:** 1
- **Дата:** 2026-10-26
- **Автор:** СА
- **Источники:** `requirements.md` (approved, 25 FR, группы A–J); ТЗ «Дневник сна ребёнка» v1.2 (§4.1–4.4, §5, §7, §8, §9) + правки v1.3 по `decisions/2026-10-26-pm-questions-v1-3.md`; `PLAN-add-core-diary.md`; `docs/ba/po-brief-add-core-diary.md`

## Зачем (проблема)

Родитель ведёт дневник сна ребёнка вручную и забывает отмечать события в моменте. Нужен рабочий фундамент Telegram-бота: родитель отмечает «😴 Заснул» / «☀️ Проснулся» (в том числе задним числом до 3 дней), бот хранит сырые события, размечает день/ночь (19:00–07:00), склеивает короткие пробуждения (порог 20 мин), отменяет последнюю отметку и подтверждает записи. Без этого фундамента невозможны окна сна и напоминания (Пакет 2) и история/настройки (Пакет 3).

## Что делаем (решение одной фразой)

Каркас слоистого бота (handlers → services → repositories) на python-telegram-bot v21 (async) + SQLite (WAL; `users`, `sleep_events`, `settings`) с хранением только сырых событий и вычислением разметки/склейки/сводок на лету, ввод задним числом с проверкой конфликтов и кнопка «↩️ Отменить последнее».

## Альтернативы (минимум 2, с trade-off)

1. **python-telegram-bot v21 (async)** — trade-off: зрелый фреймворк, встроенные `Application`/`JobQueue`, точное соответствие ТЗ §8; асинхронщина усложняет тесты. ✅ Выбрано (ТЗ §8 фиксирует PTB).
2. aiogram 3 — trade-off: удобный FSM «из коробки», но ТЗ называет python-telegram-bot, а FSM пакета минимален (состояние ребёнка выводится из последнего события, диалог ввода — в `user_data`).
3. PostgreSQL — trade-off: масштабируемость, но для персонального бота избыточен и противоречит решению 26.10 №7 (данные только на нашем сервере, рядом с ботом). ✅ SQLite WAL.
4. Хранить агрегаты (разметку/склейку) в `sleep_events` при записи — trade-off: быстрее чтение, но рассинхронизация при смене порогов; ТЗ §9.5 прямо требует расчёт на лету. ✅ Считаем на лету.

## Границы (anti-scope)

- Расчёт окон сна, «⏰ Подсказка сейчас», автонапоминания, APScheduler, вывод текста «требует проверки» (Пакет 2).
- UI настроек, `settings_history`, история за неделю, `/help`, удаление данных (Пакет 3).
- UI назначения/смены роли «наблюдатель» (схема `users.role` — в пакете, UI — позже).
- Окна дневного сна в текстах §7.2–7.4, §7.14 — не выводятся (Пакет 2).

## Влияние / затрагиваемое

- Новые модули: `src/` (handlers/services/repositories/db), `tests/` — только у dev (см. PLAN, зоны ролей).
- Миграции: первичное создание схемы БД (обратимость — на этапе каркаса не требуется, БД создаётся с нуля; последующие миграции — через `settings`-seed без разрушения данных).
- Мастер-спека `openspec/specs/` сейчас пуста — все дельты в `specs/**` идут как ADDED; при archive дельты лягут в 9 новых capabilities.
- Конвейер: dev-волны по `tasks.md` (порядок: каркас+БД → события/меню → разметка/склейка → задним числом/отмена → наблюдатель/настройки).

## Открытые вопросы, зашитые в решения (не блокируют Must)

- ОВ-ПО-1: конфликт §7.13 — принято «Изменить» = перезапись целевого события с уведомлением (рекомендация брифа). Ждёт подтверждения продакта.
- ОВ-ПО-2: сводка §7.14 в пакете 1 — только суммарные сон/бодрствование, без окон (interpretation note AC-4).
- ОВ-ПО-3: метка «требует проверки» — хранится в данных (`sleep_events`), текст не выводится (приоритет AC-2 брифа над рекомендацией брифа).
