# Аудит конвейера ai-factory (прогон флоу 1-5 + избыточность)

Класс задачи: Заказчик просит прогнать все флоу, найти избыточные ворота/контроль и аномалии, записать аудит в бэклог, исправить и пролить в оба проекта. Цикл из 6 фаз; задача закрыта только ре-аудитом, не фикс-волнами.

## Фаза 1 — инвентаризация (до субагентов)
- ls scripts/ фабрики; расшифровать ~/.hermes/cron/jobs.json (включая disabled, поля глубже верхнего уровня); grep CI-workflows обоих репо на вызовы скриптов; СВЕРИТЬ ~/.hermes/scripts/ с репо-копиями фабрики (mtime/размер/sha) — рассинхрон означает, что кроны исполняют протохший код.
- Для каждого контроля ответить: кто вызывает (CI/крон/ПМ/никто)? Дублирует ли другой слой? Ловил ли что-то за последние релизы? «Никто не вызывает» = мертвый груз — главный класс находок.

## Фаза 2 — механический прогон (субагент-исполнитель)
- Песочница: клон/копия проекта в /tmp/audit-*, НИЧЕГО не пушить; delegate_gate — в sandbox (--registry) или не трогать вовсе: он пишет в боевой реестр.
- Для каждого флоу 1-5: синтетический дифф + полный цикл flowctl (prepare/run/finish) + flow_transition check на ВСЕ переходы + IR-матрица pr_validate (каждое правило: позитив/негатив/ложное срабатывание) + краевые (повторный transition, невалидный scope/flow, stale-артефакты, зоны ролей).
- Журнал в JSONL (команда/exit/время/вердикт) — он же база ре-аудита.
- Параллельно второй субагент: семантика доков (правила-призраки — упомянуты в доках, не подкреплены скриптами; доки противоречат скриптам) + кросс-сверка с реальными инцидентами последних релизов.

## Фаза 3 — запись аудита
- Блок в BACKLOG фабрики: Наблюдения Н-N по классам (мертвые грузы / ложные блоки / молчаливые пропуски / дубли и расхождения / семантика-в-голове) + Рекомендации АУД-N с приоритетом (дешево-сейчас / средне / стратегия). Каждый Н — на воспроизведенный прогон, каждая АУД — на Н.

## Фаза 4 — фикс-волны
- Делить по ФАЙЛАМ, не по темам: волна А (flow_transition/pr_validate/flow_check/role_zone_policy), волна Б (flowctl/delegate_gate/session_check), волна В (impact_rules + НОВЫЕ модули). Конфликт стоит дороже параллелизма.
- Ворота ловят сами фикс-волны: новым тест-файлам — TC-маркеры сразу (rule 6 flow_check), иначе лишний красный CI-круг.
- Digest-пины: изменение таблицы зон в agents/README.md требует пересчета POLICY_TABLE_DIGEST в role_zone_policy.py — заложить в волну, меняющую таблицу.
- Merge серийно: ре-бейс каждой ветки на обновленный main + полный pytest на каждой.

## Фаза 5 — зеркало в проекты
- Канонический набор — COPY_FILES/FLOW_CONTROL_FILES из factory_init.py (волна обязана синхронизировать этот список).
- Проверка — scripts/check_mirrors.py --project ... (штамп match на оба проекта до merge).
- Репо-специфичные CI-правки (экспорт PR_CHANGED_* env для гейтов) — в той же зеркальной ветке; сверять flow.yml проектов ПОСТРОЧНО — расхождение = инертные ворота в одном из экземпляров.
- Крон-канонизация (если волна трогала вотчдоги/кроны): кроны обязаны исполнять репо-копии фабрики через тонкие обертки ~/.hermes/scripts (exec к main-checkout), standalone-копии — заменить обертками; установка оберток — только из main-checkout (путь к /tmp-worktree умирает при чистке); чистое состояние = пустой stdout (ok/clean-строки каждый тик = спам в чате Заказчика при deliver=origin); после правки — прямой прогон боевой обертки (пусто + exit 0).
- Exit-семантика сигнальных скриптов в кроне: обнаруженная аномалия = контент stdout (доставляется), а не exit 1 — ненулевой exit крон помечает джобу как ошибочную и шумит в списке; для CI/ручных проверок давай отдельный флаг (--strict-exit).

## Фаза 6 — ре-аудит
- Прогнать те же пробы Фазы 2 по тому же сценарию журнала; по каждому Н — фикс подтвержден/нет. Тот, кто верифицирует, обязан брать FRESH origin/main (копия, снятая до merge, дает ложное «НЕ ПОДТВЕРЖДЕН»). Боевые артефакты (обертки ~/.hermes/scripts, jobs.json) проверять на живой машине, не в песочнице. Только после этого задача закрыта.

## Ловушки
- Ворота читают рабочее дерево, а не ветку PR — вердикты меняются от чекаута; пробовать на чистом чекауте целевой ветки.
- Вердикт finish необратим по умолчанию (provisional при отсутствии PR-контекста — см. Н6) — не входить в finish без PR-контекста, если нужен финальный вердикт.
- Мелкие переносы (маркеры, точечные правки) — прямым применением правки, не cherry-pick: cherry-pick между разошедшимися линейками дает конфликты и круги угадывания.
- Не держать foreground-sleep циклы в терминале (кап 420 с рвет цикл посередине) — дробить: короткий сон + отдельная проверка.
- Тривиальные задачи (скачать/поднять/ссылка/иконка) — руками без полного конвейера: прогон мелочи через полный цикл с тремя ревью дороже самой задачи (решение Заказчика).
- Субагентам запрещено трогать AGENTS.md (guard) — правки правил агентов делает ПМ в основной сессии.
