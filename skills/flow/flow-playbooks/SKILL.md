# Playbooks флоу: нарезка пакетов и обязательный QA-контур

Когда: СА режет tasks.md нового пакета, ПМ планирует этапы, ПМ принимает возвраты (return ревьюера, баги QA-раннеров). Скилл закрывает инцидент add-wiki (J39): QA-артефактный контур выпал из плана пакета — ворота поймали только на финальном PR, кейсы писались задним числом от кода.

## Разбор задачи на входе: размер решает инструмент

- До объявления флоу оцени задачу на тривиальность: «склонировать репо, поднять, добавить ссылку/иконку» или любая задача в 1-2 прямых команды/правки — исполняй руками без конвейера (клон/запуск/правка/пуш одним заходом). Конвейер (СА, ревью, CI-циклы) стоит дороже самой задачи; прогнанная через полный Флоу тривиальность — прямой вопрос Заказчика «я просил просто скачать и запустить». Конвейер — для задач, где есть код, контракт или регресс.
- Одиночные точечные правки (маркеры тестов, строки доков, мелкие порты) переноси ПРЯМОЙ правкой на целевой ветке, не cherry-pick'ом: ветки с расходившейся линейкой дают конфликты на каждом пике, а разбор «тот ли коммит» съедает больше кругов, чем стоит сама правка. Cherry-pick — только для многофайловых коммитов между близкими ветками.
- Перед пушем зеркала/переноса на существующую ветку проверь ее lineage (`git log --oneline -5 <ветка>`): имя ветки не гарантия содержимого — ветка с «чужим» именем может нести чужую линейку коммитов, и зеркало уедет туда незамеченным.

## Правило выбора файла

Флоу объявляется ПМ до старта пакета (памятка ПМ п.2). СА при нарезке читает файл СВОЕГО флоу в каталоге `references/flows/` этого скилла: `flow-1-full.md` (полный: БА → СА → дизайн → dev → QA → приемка), `flow-2-bugfix.md`, `flow-3-hotfix.md`, `flow-4-maintenance.md`, `flow-5-express.md`. Общие правила (ворота, маркеры PR, зоны, возвраты) — в этом SKILL.md; специфика флоу — в его файле. Чужие файлы флоу не читать — они про другой цикл.

## Обязательные задачи tasks.md при нарезке (Флоу 1, пакеты с дельтами)

Эталон нарезки — add-responsive-mobile: impact → чеклист → кейсы → ревью кейсов → автотесты. Пакет Флоу 1 ОБЯЗАН содержать (или в явном QA-этапе):

1. `[tests] qa_impact_analysis` — impact-анализ (`test-model/impact/<id>.md`) при MODIFIED/REMOVED дельтах (H5).
2. `[tests] qa_checklist` — чеклист (`test-model/checklists/<id>.md`) — статус по J23 (кандидат на упразднение; пока этап существует — задача обязательна).
3. `[tests] qa_author` + `[tests] qa_case_reviewer` — кейсы (`test-model/new/` → `approved/`) с независимым ревью.
4. `[tests] qa_automation` — автотесты/прогон по наборам, TC-ID в каждом тесте (`TC-<change>-NNN`, правило 6 flow_check). Ловушки правила 6: маркер должен лежать ВНУТРИ docstring теста (вставленный строкой выше парсится как выражение — ведущие нули `TC-X-001` = SyntaxError) и номер строго 3-значный (regex `\d{3}` — `TC-X-01` rule 6 не засчитает).

Нарезка ДОЛЖНА идти «кейсы до автотестов»: qa_author раньше qa_automation. ЭТАП QA, состоящий только из раннеров «прогнать наборы», — ДЕФЕКТ плана; СА не отдает tasks.md без QA-контурных задач, ПМ не принимает.

## Проверка перед стартом QA-этапа (чек-лист ПМ до диспатча раннеров)

1. `test-model/checklists/<id>.md` существует и покрывает все Requirements дельт.
2. Кейсы написаны из дельт спеки (не из готового кода).
3. Кейсы прошли qa_case_reviewer (new/ → approved/).
4. Каждый автотест несет TC-ID, трассируемый к кейсу.
5. На пакетах после add-wiki: независимый аудит покрытия «сценарий дельты → кейс → тест» (как REPORT-coverage-audit) до прод-выкатки.

## Роль BA: необязательна при дословной заявке Заказчика

Артефакт requirements.md воротами НЕ требуется (pr_validate проверяет только impact/approved-cases/reviews/regress-final). Когда Заказчик пишет требования дословно в чате — его заявка в бэклоге ЕСТЬ requirements (ноль искажений пересказом), роль BA не включай; фиксируй в пакете запись «BA выполнен Заказчиком, requirements = дословная заявка». BA включай только когда требования надо собирать из разрозненных кусков.

## Ветка пакета: PR только на полном пакете

Артефакты Флоу 1 копятся на ветке `pipeline/<change-id>` через ВСЕ волны (БА → СА → архитектор → dev → QA) — PR открывается только когда пакет полон (proposal + specs + design + tasks). Ранний PR с change-маркером честно краснеет в check_change на недостающих артефактах следующих этапов (flow_check на repo-уровне то же) — это не ложная тревога, а правильно работающие ворота: не пересобирай пакет под CI, собирай пакет.

## Возвраты с этапов

- **return code_reviewer**: фикс-дифф → ре-ревью коротким кругом (тот же ревьюер, append-only review-NNN+1); чекбокс [x] закрывается ТОЛЬКО после финального approve (approved_review_tasks берет последний вердикт — старый approve перезаписывается return'ом).
- **Артефакт итерации ревью обязан быть ЗАКОММИЧЕН до merge.** Ревьюер-сабагент может записать review-NNN+1 в рабочее дерево и не закоммитить (verdict в чате есть, файла в ветке нет) — перед merge проверяй `git log --oneline -1 -- code-reviews/<id>/` и наличие файла последней итерации; при отсутствии фиксируй сам из отчета делегации с атрибуцией Reviewer-Delegation (id делегации в сообщении коммита) — вердикт последней итерации без файла в ветке = дыра в append-only истории.
- **Тонкий вердикт делегации — читай артефакт из ветки.** RETURN/approve сводкой без находок («verdict: return», пусто) — вердикт-файл в ветке содержит полный разбор: чекаутни ветку и прочитай review-файл ДО ре-диспетчеризации; фиксу передавай конкретный чек-лист находок (F1/F2/…), а не «исправь по ревью» — иначе фикс-агент перечитывает ревью сам и теряет контекст мандата.
- **баг QA-раннера**: баг-репорт (`test-model/bugs/BUG-NNN`), набор останавливается до фикса и зеленого перегона; фикс через Флоу 2 (code_review обязателен — решение 2026-10-07-code-review-flow2); повторный прогон набора — отдельной делегацией.
- **GAP аудита покрытия** (сценарий дельты без кейса/теста): Must-сценарий = блокер следующего этапа (деплой/архивация), Should/Could — фикс или принятый риск с пометкой в tasks.md.
- **rework мокапов Заказчиком**: новый мокап → повторный design_validation после фикса.

## Merge-гигиена ПМ (ловушка тайминга)

- Follow-up коммит, запушенный в ветку ПОСЛЕ merge ее PR, уходит в мертвую ветку — в main он не попадает, а «push прошел» создает иллюзию доставленности (ловушка срабатывает на длинных цепочках «пуш → sleep → CI → merge», где CI-ожидание перемежается доправками). Перед любым пушем — `gh pr view <n> --json state`; опоздавший коммит — cherry-pick на новую ветку от origin/main отдельным PR.
- Minor-замечания ревью (однострочники доков) правь ДО merge в той же волне, не после: каждый после-merge-круг — это второй CI-цикл (у e2e ~4–5 мин) и второй PR, ради одной строки.
- Ожидание CI не держать одним foreground-вызовом терминала со sleep'ами (кап вызова срывает команду в фон посреди цепочки merge): цикл «sleep ≤240 + gh pr checks» отдельными вызовами или фоновый процесс с уведомлением о завершении.

## Волны фиксов по аудиту/ревью (параллельная разборка)

- Найденные недостатки (аудит ворот, приемка, ретро) записывай единым блоком с нумерованными ID (наблюдение Н-N → рекомендация R-N) в бэклог — это план разборки; фиксы — параллельными dev-волнами по НЕПЕРЕСЕКАЮЩИМСЯ файловым зонам, ветки от одной базы.
- Слияние волн серийное (A merge → B rebase на новый main → merge → C …); после каждого merge — полный pytest на ветке следующей волны до PR; новый тест-файл волны СРАЗУ с TC-маркерами в docstring (rule 6 краснит CI — ворота ловят саму волну фиксов).
- Фиксы скриптов/ворот после merge зеркалятся во ВСЕ проекты-потребители (механика сверки хешей копий — scripts/check_mirrors.py), затем контрольный перегон исходного аудита на новой версии — «недостаток закрыт» без повторного прогона это слово, не факт.
- Вотчдоги/кроны: правь политику доставки ДО изменения частоты/канала (no_agent-крон с непустым stdout на каждый тик при deliver=origin — спам Заказчику каждые N минут; чистое состояние = пустой stdout = тишина).

## regress-final и приемка (J51.3)

- После QA-контура и до merge — regress-final: выделенный сабагент
  (regress_runner/qa_runner, НО роль в маркере делегации — dev для
  chore-графа) с узким брифом: ветка/коммит/затронутые сьюты — контекст
  релиза не нужен. Запуск `flowctl regress --change <id> --final`, FAIL →
  изолированный перепрогон 2× (баг vs флак), артефакт
  `test-model/regress/<change>/regress-final.md` коммитится в ветку.
- Артефакт обязан быть СВЕЖЕ относительно всех измененных файлов PR, кроме
  самих регресс-артефактов: любой коммит в PR после прогона (flow.yml,
  тесты, зеркало) = STALE → перезапуск runner'а на новом HEAD.
- **Порядок сборки релизной ветки: артефакт регресса — ПОСЛЕДНИЙ коммит.**
  Все test-model-артефакты вноси ДО запуска финального прогона: кейсы →
  УТВЕРЖДЕНИЕ Заказчиком → approved/, QA-отчет, ревью кейсов
  (`test-model/reviews/<id>/`, контракт 5), impact-проекция H5
  (`test-model/impact/<id>.md` при MODIFIED/REMOVED дельтах), финальный бамп
  static_v. Пропущенный артефакт после прогона = честный перегон (~15 мин):
  запрашивай утверждение кейсов Заказчиком заранее, а не после регресса.
- regress_runner пишет только в test-model/regress/; найденные продуктовые
  баги — возврат dev'у с баг-репортом, не фикс сам.

## Impact-карта (J58): честность проверяется кодом, не памятью

- Перед «X не затрагивается» в impact.md — grep по коду на этот путь/поведение:
  находка P23 (заявлено «is_fast только при создании», реальность — PATCH FR-89
  + чекбокс в edit-форме = третий путь вставки) стоила круга СА.
- Существующие тесты, ассертящие старое поведение изменяемой фичи, СЛОМАЮТСЯ —
  вноси их в карту и в dev-волну (правки тестов), строка «существующие тесты
  зелеными без изменений» в impact-карте = красный флаг, проверь прогоном.
- Проекция H5 (`test-model/impact/<id>.md`) пиши рано (до финального регресса),
  иначе поздний коммит = STALE-перегон. Механический гейт J58 (IR-01…04) ловит
  на CI: статика фронта без бампа static_v, новый каталог services/ без
  deploy-матрицы — DENY с подсказкой.
- Дорогие проверки ставь ДО дорогого действия, а не в его воротах: свежесть
  regress-артефакта и факт бампа static_v сверяй перед запуском 15-25-минутного
  прогона, а не в merge-воротах после него; pre-flight дешевле честного
  перегона. Механика: `scripts/flow_preflight.py` (static_v / regress-staleness /
  pr-body-требования IR-05/06 / привязка снапшота к checkout), `flow_scope_check.py`
  (коммиты ветки vs change-id), `check_mirrors.py` (копии скриптов vs эталон);
  IR-05 (Dockerfile → сборка образа в PR) и IR-06 (контент-ассеты → URL+sha) —
  в impact_rules.json (pr_body-требования проверяются preflight'ом, не merge-воротами).
- Верификация деплой/образных изменений — СБОРКОЙ образа, не маунтом файлов:
  ревью-стенд, монтирующий конфиги напрямую в контейнер, не ловит отсутствие
  файла в COPY Dockerfile (CI собирает образ и падает на старте сервиса) —
  ревью-метод обязан повторять CI-метод сборки, иначе оба зеленые при битом
  образе.

## UX-фича: дизайн-фаза прежде спеки

- Пакет, меняющий пользовательский интерфейс, обязан начинаться с мокапов
  (ui_designer) и их сверки Заказчиком ДО нарезки dev-задач; dev работает
  только по УТВЕРЖДЕННЫМ макетам. Архитектура без проектирования UX =
  отклонение на живой приемке (богатый движок не спасает от неправильного
  интерфейса). Для такого продукта предпочти готовую библиотеку самописному
  движку, если задача попадает в решенный класс.
- Приемка бывает финальной: Заказчик вправе сказать «доведи до конца,
  финал приму» — тогда per-wave живые приемки заменяются стенд-верификацией
  агентов, а живая приемка одна, в конце (после деплоя). Отражай это в
  tasks.md (живая приемка только финальная) и не дергай Заказчика
  промежуточно.
