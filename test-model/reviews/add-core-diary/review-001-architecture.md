## 2. Реализуемость порядка волн

Порядок «каркас → события/меню → разметка/склейка → задним числом/отмена → observer/настройки» в целом корректен: undo (2.4) не зависит от склейки (удаляет сырые события, склейка пересчитывается на лету); backfill-волна опирается на сводку 3.4; конфликты (4.4) идут после парсера (4.2) в той же волне, порядок внутри волны по нумерации задач восстанавливает зависимость. Найденные скрытые зависимости вынесены в findings (F-1, F-8).

## 3. Findings

Severity: **blocker** — блокирует approve; **major** — обязательно исправить до старта dev-задач; **minor** — исправить при доработке пакета; **note** — зафиксировать, не блокирует.

### F-1 (major) — D6 противоречит FR-3/ТЗ §9.5 и нереализуем в момент записи события
- **Где:** design.md D6; FR-3; задача 1.3 (готовность: «пишутся только сырые поля… sleep_type»), задача 2.3.
- **Суть:** D6: «sleep_type пишется в момент записи события (day/night/null по правилу FR-9/10/11)». FR-3 и ТЗ §9.5 прямо требуют: разметка день/ночь вычисляется **на лету**, не хранится заранее. Кроме противоречия, правило записи нереализуемо корректно: при «😴 Заснул» → «🕐 Сейчас» конец интервала неизвестен, а правило FR-9 зависит от конца («конец ≤ 07:00»), FR-11 — от длительности (< 40 мин). Дополнительно: при смене настроек границ ночи (FR-24) сохранённый sleep_type устареет без пересчёта.
- **Рекомендация:** sleep_type — чистая функция от интервала на лету (в схеме поле оставить как «сырое», при записи null); либо явно зафиксировать в D6: «финализируется при завершении интервала (wake/задним числом)» + пересчёт/игнорирование при смене настроек. Поправить D6, готовность задачи 1.3 и поведение 2.3 (сейчас 2.3 идёт в волне 2, разметка — в волне 3: скрытая зависимость, при записи неклассифицируемо).

### F-2 (major) — FR-12/D8: двусмысленность отнесения сна, начинающегося в [00:00; 06:00)
- **Где:** design.md D8; FR-12 (сценарий «Сон до 06:00»); задача 3.2 (готовность).
- **Суть:** D8 использует два правила сразу: «день интервала = локальная дата **начала** сна» и «страница дня = 06:00 → 05:59». Для сна 22:10 → 07:20 они совпадают (день 10.10). Для сна, начинающегося в 01:00–05:30 утра (например, 02:00 → 05:30 того же утра), правила расходятся: по дате начала — текущий день, по странице 06:00 — предыдущий. Сценарий FR-2 «сон, заканчивающийся в 05:30 → предыдущий календарный день» не определяет, о каком времени начала речь. От этого зависит сводка за день (FR-19, задача 3.4) — критерий приёмки неоднозначен.
- **Рекомендация:** выбрать и зафиксировать одно правило (рекомендация: отнесение по странице дня, т.е. локальная дата момента (timestamp − day_start)); добавить юнит-тест на сон с началом в [00:00; 06:00) в задачи 3.2/3.4.

### F-3 (major) — D5 опирается на ложный инвариант Telegram: «нажатие противоречащей кнопки невозможно физически»
- **Где:** design.md D5; FR-6; задачи 2.2/2.3.
- **Суть:** устаревшие inline-клавиатуры в истории чата остаются нажимаемыми: колбэк от старой кнопки («😴 Заснул» из предыдущего сообщения) придёт и в состоянии «спит». Нажатие «невозможно физически» только в пределах текущего сообщения. Без защитной проверки возможны противоречивые события (двойной sleep, wake без sleep).
- **Рекомендация:** в D5 и задачах 2.2/2.3 зафиксировать guard: обработчик событийного колбэка перепроверяет состояние (D5-вывод) и при противоречии игнорирует нажатие с обновлением меню (answerCallbackQuery + перерисовка клавиатуры).

### F-4 (minor) — статус ОВ-ПО-1/ОВ-ПО-3 противоречит между документами
- **Где:** requirements.md (корень, §7: «решённые продактом 26.10: перезапись при конфликте…») vs openspec requirements.md §3 («Требует подтверждения продакта») vs design D11 / proposal («финальное подтверждение — за продактом»).
- **Суть:** FR-18 (approved, Must) строится на перезаписи целевого события, но один документ называет решение принятым, другой — ожидающим подтверждения. Перед dev должна быть одна версия: либо «Одобряю» продакта закрывает ОВ-ПО-1/3, либо FR-18 помечен как черновое поведение.
- **Рекомендация:** синхронизировать §3 openspec requirements.md и D11 с корневым requirements.md (или наоборот), зафиксировать дату/канал подтверждения.

### F-5 (minor) — неверные цитаты «решение №1» для перезаписи при конфликте
- **Где:** sdd.md §4 («перезапись целевой записи (решение №1)»); requirements.md (корень, §7: «перезапись при конфликте (№1/ОВ-ПО-1)»).
- **Суть:** в decisions/2026-10-26-pm-questions-v1-3.md №1 — это «целевая длительность дневного сна». Перезапись при конфликте — это ОВ-ПО-1 (рекомендация брифа, отдельный контур подтверждения), а не пронумерованное решение продакта. Смешение нумерации приведёт к ложной трассировке «переписывание события утверждено продактом ответом №1».
- **Рекомендация:** цитировать как «ОВ-ПО-1, рекомендация брифа, подтверждение — продакт» (в design D11 сделано верно — выровнять sdd.md и корневой requirements.md).

### F-6 (minor) — в репозитории лежит ТЗ v1.2, документы ссылаются на v1.3
- **Где:** ТЗ_Дневник_сна_ребёнка.md (шапка «Версия 1.2»); в §5 — 12 настроек, в §6 меню без «↩️ Отменить последнее», §13 — «роли» в будущем; requirements/design ссылаются на «ТЗ v1.3 (правки по decisions 26.10)».
- **Суть:** все правки v1.3 существуют только в decisions-файле; первоисточник не обновлён. Следующий ревьюер/дев, читая ТЗ §5/§6/§13, получит устаревшие факты (12 настроек, меню из 5 кнопок, роли «не сейчас»).
- **Рекомендация:** обновить файл ТЗ до v1.3 (вне зоны архитектора — через СА/ПМ) либо явно пометить в требованиях: «v1.3 = файл v1.2 + decisions/2026-10-26».

### F-7 (minor) — D11: не определён выбор «целевого» события при нескольких конфликтах; потеря данных после «Изменить» + «Отменить последнее»
- **Где:** design.md D11; FR-18.
- **Суть:** (а) при нескольких пересечениях не сказано, какая запись «целевая» для перезаписи (§7.13 показывает одну); (б) при нарушении порядка sleep/wake неясно, что перезаписывается; (в) после перезаписи «↩️ Отменить последнее» (D12 — DELETE по created_at/id) удалит перезаписанную запись целиком — исходное событие не восстановится (soft-delete отклонён осознанно, но взаимодействие двух механизмов не описано).
- **Рекомендация:** зафиксировать: целевое = ближайшее конфликтующее событие (детерминированный выбор), при нарушении порядка — перезапись последнего события, приводящего к нарушению; задокументировать, что undo после «Изменить» не восстанавливает прежнее значение.

### F-8 (minor) — нет явной задачи на построение интервалов из сырых событий
- **Где:** tasks.md волна 3; ТЗ §10.5 CalculationService.build_sleep_intervals.
- **Суть:** задачи 3.1/3.3/3.4 оперируют «интервалами сна», но функция, превращающая сырую последовательность sleep/wake в интервалы (незакрытый сон на границе дня, некорректные последовательности после задним-числом-ввода/undo), не выделена и не имеет критерия готовности — скрытая зависимость всех расчётов волны 3.
- **Рекомендация:** добавить в 3.3 (или отдельной задачей) построение интервалов с юнит-тестами: незакрытый sleep, wake без sleep, события вне хронологического порядка.

### F-9 (minor) — схема не связывает наблюдателя с родителем
- **Где:** design.md D3/D13; FR-22; sdd.md §3.
- **Суть:** users.role есть, но нет связи observer → родитель (family/parent_id). FR-22 требует: наблюдатель видит сводки «так же, как родителю» — в пакетах 2–3 для этого понадобится additive-миграция и правило, чьи события смотреть. Тезис решения №5 «закладываем сейчас — дёшево» выполнен наполовину: роль есть, linkage — нет, и это нигде не зафиксировано как планируемое расширение.
- **Рекомендация:** добавить в D13/impact.md явное допущение: «связь наблюдателя с владельцем данных — additive-миграция в пакете 2/3; в пакете 1 role хранится, UI и linkage отсутствуют».

### F-10 (note) — часовой пояс: карта language_code и DST не детализированы
- **Где:** design.md D4, «Допущения»; риск признан в PLAN.
- **Суть:** карта «ru → Europe/Moscow» покрывает носителей ru в Украине/Беларуси/Казахстане (сдвиг до +2 ч искажает границы 19:00/06:00 и разметку) — допущение помечено «не проверено», приемлемо как first approximation, но сама карта (список кодов) в design не приведена и не тестируется. DST-переходы: локальное время «вчера 02:30» в ночь перевода часов может быть несуществующим/дублирующимся — парсер (4.2) это не покрывает.
- **Рекомендация:** зафиксировать карту кодов в design как артефакт кода с юнит-тестом; для DST — задокументировать правило выбора (fold=0) или отклонение ввода.

### F-11 (note) — is_merged никогда не проставляется
- **Где:** ТЗ §9.2; задача 1.3 (готовность перечисляет is_merged среди записываемых полей); D9 (склейка — только вычисление).
- **Суть:** при склейке на лету флаг is_merged не имеет момента записи — поле останется пустым всегда. Риск: dev будет искать несуществующую логику записи.
- **Рекомендация:** пометить в D9/D14: is_merged — резерв схемы, в пакете 1 не пишется. Аналогично: константы warn_gap=10 мин (задокументированное допущение) и порог 40 мин из ТЗ §4.2 — допустимые константы, задача 5.2 уже учитывает исключения.
