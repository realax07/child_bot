# core-storage

## ADDED Requirements

### Requirement: Слоистая архитектура (FR-1)

Система SHALL быть разделена на слои handlers → services → repositories; обработчики Telegram (handlers) SHALL NOT обращаться к хранилищу напрямую — только через сервисы; бизнес-логика (разметка, склейка, расчёты) SHALL быть отделена от интерфейса (ТЗ §8, §10.1).

#### Scenario: Разделение слоёв
- **WHEN** реализуется новое поведение дневника (событие, разметка, склейка)
- **THEN** логика вычислений находится в service-слое и вызывается из handler'ов, доступ к БД — только через repositories

### Requirement: База данных SQLite WAL (FR-2)

Система MUST использовать SQLite в режиме WAL со схемой из трёх таблиц: `users`, `sleep_events`, `settings` (ТЗ §9.1–9.3; решения 26.10 №7). Таблица `users` дополнительно содержит `role` (см. access-roles).

#### Scenario: Инициализация БД
- **WHEN** бот запускается первый раз (БД отсутствует)
- **THEN** создаются таблицы `users`, `sleep_events`, `settings` в соответствии с ТЗ §9.1–9.3, включён WAL

### Requirement: Хранение сырых событий (FR-3)

`sleep_events` MUST хранить сырые события (event_type sleep/wake, фактический timestamp, created_at, is_backfilled, sleep_type, is_merged — ТЗ §9.2). Разметка день/ночь, склейка и суммарные показатели MUST вычисляться на лету из сырых событий, а не храниться заранее (ТЗ §9.5). Колонки `sleep_type`/`is_merged` — резерв схемы: при записи заполняются NULL; `sleep_type` вычисляется при чтении/расчёте (зависит от конца интервала и настроек).

#### Scenario: Событие фиксируется как есть
- **WHEN** родитель отмечает любое событие (кнопкой или задним числом)
- **THEN** в `sleep_events` появляется запись с фактическим временем события и признаком способа ввода; никакие вычисленные агрегаты в запись не пишутся

#### Scenario: sleep_type при записи не вычисляется
- **WHEN** родитель нажал «😴 Заснул», затем «🕐 Сейчас» (конец интервала неизвестен)
- **THEN** запись события содержит sleep_type = NULL; разметка day/night вычисляется при чтении
