# Ревью кода

Как независимо валидировать реализацию одной задачи: соответствие спеке, качество, безопасность. Ревью — не формальность и не охота: цель — пропустить корректный код и поймать расхождение со спекой до того, как оно ляжет в основу следующих задач.

## Когда применять

- Реализована задача tasks.md, dev-агент отчитался
- Найден дефект и нужно проверить исправление (повторное ревью)

Не применять для: ревью тест-кейсов (это `case-review`), ревью спек (проверка контракта 2), ревью всего репозитория (только задача).

## Процедура

1. **Определи масштаб:** диф задачи (коммит/коммиты с номером задачи), задетые файлы, какие Requirement/Scenario она реализует (из tasks.md → спека). **Из ТЗ возьми процедуру проверки (команда/сценарий воспроизведения); если в ТЗ её нет — верни задачу ПМ с пометкой «нет процедуры проверки», не ревьюй по наитию.**
2. **Первый круг — спека как закон:**
   - каждое Scenario задачи реализовано? (включая негативные — их забывают чаще);
   - модальность: MUST выполнено всегда, SHOULD отклонения обоснованы в design.md;
   - API-пути, схемы, коды ошибок совпадают с sdd.md дословно;
   - нет поведения вне спеки («улучшений» мимо трассировки).
3. **Второй круг — best practices:**
   - изоляция: побочные эффекты локализованы, глобальное состояние не мутируется;
   - обработка ошибок: ошибки не глотаются; пользователь видит коды из sdd, не стек-трейсы;
   - секреты: в коде/логах/тестовых данных нет паролей и ключей; конфиг через env;
   - инъекции: SQL — только параметризованные запросы (особенно advanced-фильтр поиска!); XSS — экранирование пользовательского вывода;
   - данные: файл БД/логи не попадают в git (NFR-5);
   - читаемость: имена по домену, функции короткие, дубли не размножены.
3a. **Performance (J45+, pr-review-expert):** нет N+1 запросов на циклах; новые паттерны запросов покрыты индексами; нет неограниченных циклов на потенциально больших наборах (задачи, страницы wiki); тяжелая новая зависимость — с обоснованием в design; асинхронные операции корректно awaited.
4. **Третий круг — integration-точки:** задача не сломала соседние сценарии (быстрый смоук смежных Requirements), миграции схемы согласованы с sdd.
4a. **Blast radius + breaking changes (J45+, pr-review-expert):**
   - кто импортирует измененные модули — проверено (grep импортеров);
   - env-переменные: новые задокументированы (README/RUNBOOK), удаляемые — не используются в проде;
   - миграции БД обратимы (откат = предыдущий релиз работает на мигрированной схеме или есть down-путь); **необратимая миграция прод-данных без явного rollback-плана в deploy-RUNBOOK = blocker** (шаги отката, точка восстановления, критерий «откат завершен» — источник: migration-architect, claude-skills 2026-10-13);
   - удаление/изменение API-эндпоинтов — с deprecation-пометкой или согласовано; обязательные поля в существующих ответах не добавлены (обратная совместимость потребителей).
4b. **Adversarial-персоны — для значимых диффов (J45+, adversarial-reviewer):**
   прод-пакет, новый домен/сервис, изменение auth/данных → прогони три персоны,
   каждая ОБЯЗАНА найти ≥1 замечание («LGTM не проходит»):
   - **Саботажник** — «сломаю это в проде»: конкурентные записи, порядок деплоя, кеш, недоступность соседних сервисов;
   - **Новичок** — «объясни через месяц»: непонятные имена, магические значения, неочевидные инварианты без комментария/ссылки на спеку;
   - **Security-аудитор** — OWASP-ось: authz на новых эндпоинтах, инъекции, загрузки, секреты, заголовки.
   Замечание, пойманное 2+ персонами, повышает серьезность на ступень. Вердикт: BLOCK/CONCERNS/CLEAN — маппится в approve/return.
5. **Документация в диффе** (README, deploy-инструкции, миграционные шаги): команды проверяются **буквальным воспроизведением в чистой среде** (пустая директория/свежая БД), чтением «глазами» не проверять — нерабочая команда выглядит корректно на бумаге (урок 1.4 и развертывания 2026-09-19).
6. **Вердикт:** «approve» — задача может вливаться; «return» — таблица замечаний (файл/строка/серьезность/рекомендация). Blocker — нарушение спеки, security, потеря данных; major — нарушение практик с риском; minor — стилистика.
7. **Исправление и повтор:** dev чинит по замечаниям → повторное ревью диф-а исправления. История ревью append-only.

## Отчет

Структура: вердикт → таблица замечаний (blocker/major/minor) → проверенные Scenario → что НЕ проверено (честно). Замечание без рекомендации = неполное замечание.

## Анализатор качества кода (J45+, vendor: code_quality_checker.py)

Объективные метрики структуры — дополняют круги ревью числами, не мнением:

```bash
# по файлу/каталогу (python-проект)
python skills/code-review/scripts/code_quality_checker.py <path> --language python

# JSON-выдача для review-файла
python skills/code-review/scripts/code_quality_checker.py <path> --language python --json
```

| Метрика | Порог |
|---|---|
| Long function | >50 строк |
| Large file | >500 строк |
| God class | >20 методов |
| Too many params | >5 |
| Deep nesting | >4 уровней |
| High complexity | >10 ветвлений |

- Находки long_function/high_complexity — легитимные замечания ревью (major, если файл из §6 долга карты).
- HTTP-статус-коды (100–599) и docstring-строки исключены из magic_number (J45-tuning: FastAPI-проект).
- Вендорный скрипт (MIT, из alirezarezvani/claude-skills, code-reviewer); тюнинг ai-factory помечен в коде. Апстрим-дифф: `_parse_pip` ищет requirements.txt только в корне — monorepo (backend/requirements.txt) не видит; для нас не критично, считаем известным ограничением.

## Ошибки

- Ревью «по диагонали» больших диф-ов — лучше попросить оркестратора разбить задачу, чем пропустить blocker.
- Предлагать архитектурные переделки вне задачи — ревьюер не автор; сомнение → комментарий, не вердикт.
- Пропуск негативных сценариев при проверке — самый частый брешь.
- Править код самому вместо замечаний — ревьюер теряет независимость.
