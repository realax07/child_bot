# Запуск ПМ-сабагента: механика (J1/J2, блок J)

> Дизайн-документ механизма. Статус: спроектировано (J1/J2/J3, 2026-09-26), внедрение — поэтапно (раздел «План внедрения»). Читается ПМ-сабагентом (п.6 входа) и relay-сессией.

## 1. Модель: relay-паттерн (J1)

После J1 в системе две сессии вместо одной:

```
Заказчик ⇄ [ОСНОВНАЯ СЕССИЯ Hermes = relay] ⇄ [ПМ-сабагент (delegate_task)] ⇄ роли-сабагенты
```

- **Основная сессия (relay)** — тонкий клиент: диалог с Заказчиком, резюме диалога в бриф, передача эскалаций, финальная приемка эскалированных решений. Больше ничего. НЕ запускает роли, НЕ читает код проекта, НЕ ведет PLAN.
- **ПМ-сабагент** — весь оркестраторский цикл: спавн ролей, пинги, приемки, PLAN/BACKLOG, push.
- Роли-сабагенты не меняют_launcher'а: их спавнит теперь ПМ-сабагент (delegate_task доступен сабагентам — проверено: роли уже спавнятся из основной сессии, которая сама является агентом; вложенность Hermes работает).

### Почему delegate_task, а не «вторая основная сессия»

| Вариант | Изоляция контекста | Жизненный цикл | Журналирование | Вердикт |
|---|---|---|---|---|
| `delegate_task` с долгой фазой мониторинга | полная (доказано AGENTS.md «Оркестрация») | живет, пока жива задача; результат возвращается отчетом | отчет + PLAN + active_sessions | **да** |
| Вторая интерактивная сессия Hermes | да | требует ручного обслуживания Заказчиком | ручное | нет (операционная нагрузка) |

delegate_task — уже проверенный примитив (все 13 ролей); J1 не вводит новую инфраструктуру, а применяет существующую к роли ПМ. Долгие фазы (цикл задач с пингами каждые 5–10 минут) — штатный режим фоновых делегаций (прецедент: делегации E9/E16 по 30–50 минут).

### Контракт обмена с relay (что передается и как)

| Направление | Что | Носитель |
|---|---|---|
| relay → ПМ | Стартовая задача: goal по п. «Запуск» ниже | параметр задачи делегации |
| relay → ПМ | Ввод Заказчика в ходе фазы: дословная цитата + указание, в какую делегацию/задачу | **новая делегация-продолжение** (see §2) |
| ПМ → relay | Отчет: что закрыто (коммиты), эскалации нумерованным списком с вариантами, что предлагается запустить дальше | результат delegate_task |
| ПМ → relay | Срочный стоп (деградация, инцидент) — не дожидаясь конца фазы | НЕ поддерживается протоколом (см. риски, §6) |

## 2. Запуск (форма goal)

```text
РОЛЬ: agents/pm_agent.md (прочитай первым действием)
ПРОЕКТ: <имя репо проекта, напр. ekotov-wiki>
ПУТИ: фабрика /home/openclaw/ai-factory; проект /home/openclaw/<репо>
ФЛОУ: <1|2|3|4|5> — правило плана задачи (2026-09-20): флоу зафиксирован Заказчиком
ЗАДАЧА: <что запущено Заказчиком: фаза/этап, дословные цитаты решений>
ГОРИЗОНТ: <до какого события работать: «все задачи tasks.md до QA-контура» / «одна задача 4.1»>
ЭСКАЛАЦИИ: <что уже решено делегировано ПМ («интерпретация ПМ» с основанием), что — нет>
ОТЧЕТ: коммиты, эскалации нумерованным списком, статус PLAN, предложение следующего шага.
ГРАНИЦЫ: agents/pm_agent.md, раздел «Границы»; диалога с Заказчиком у тебя нет.
```

Лимит ≤2500 символов (правила экономии task_delegation.md действуют). Всё остальное ПМ-сабагент читает из файлов.

### Ввод Заказчика в ходе фазы

ПМ-сабагент работает фазой автономно; дословные ответы Заказчика на эскалации relay передает **новой задачей тому же шаблону** (заголовок «ПРОДОЛЖЕНИЕ: <id фазы>» + дословные цитаты). Прерывать живую delegate_task вводом нельзя — это фундаментальное ограничение и осознанный компромисс дизайна (см. риски). Смягчение: relay формулирует эскалации пакетно, а ПМ-сабагент проектирует фазы так, чтобы точки эскалации совпадали с естественными паузами (конец цикла задач, конец QA-партии).

## 3. Реестр сессий с project-полем (J2)

`~/.hermes/state/active_sessions.json` (вне git, ведение — правило 10 AGENTS.md). Новая схема:

```json
{
  "_comment": "Активные сессии сабагентов (F2 + J2). Поля project/owner_pm введены J2. Вне git.",
  "sessions": [
    {
      "delegation_id": "deleg_...",
      "role": "dev",
      "project": "ekotov-wiki",
      "owner_pm": "pm-ekotov-wiki",
      "flow": 1,
      "started": "2026-09-26",
      "status": "running",
      "zone": ["backend/app/**"],
      "worktree": "/home/openclaw/ekotov-wiki-worktrees/deleg_x"
    }
  ]
}
```

Правила J2: (а) `project` и `owner_pm` — обязательные поля каждой записи; (б) ПМ-сабагент читает/пишет ТОЛЬКО записи своего `project` (чужие — только как «чужие зоны» при проверке пересечений, п.8 шаблона делегации); (в) один ПМ = один проект; параллельный проект = второй ПМ-сабагент со своим PLAN.md/BACKLOG-курсом и своим relay-контекстом. Переход на новую схему — миграционный скрипт (см. §7), старые записи без `project` получают `"project": "ai-factory"`.

## 4. Что остается в основной сессии (обязательство relay)

1. Диалог с Заказчиком (единственный носитель канала).
2. Резюме диалога → бриф запуска (§2).
3. Эскалации: показать Заказчику, собрать ответ, вернуть новой делегацией.
4. Контроль расхода:relay решает, когда фаза заслуживает запуска (ворота фаз).

Всё остальное — анти-паттерн после J1: relay НЕ спавнит роли, НЕ приемлет работу, НЕ правит PLAN.

## 4.1 Диспатч debug-агента (J35)

Застрявшая делегация (needs-debug эскалация от роли или 3+ итерации без прогресса
по транскрипту) → ПМ запускает debug-агента ПАРАЛЛЕЛЬНО задаче-источнику (не вместо,
не с остановкой): goal = факты (что делалось, что наблюдалось), зона — только
диагностика, вердикт СРЕДА/КОД/ТЕСТ. Запись задачи-источника: эскалация в
lifecycle-history. База граблей: docs/project-pitfalls.md.

## 5. Проверка живости ПМ-сабагента (пинг relay → ПМ)

Relay пингует ПМ-сабагента симметрично тому, как ПМ пингует роли: `tail -c 800 ~/.hermes/cache/delegation/live/deleg_<pm>/task-0.log` каждые 5–10 минут. Здоровье = tool-вызовы по файлам проекта, записи в журнал PLAN. Деградация = петли фраз / отсутствие tool-вызовов → relay фиксирует инцидент, останавливает, перезапускает по goal §2 (состояние ПМ не теряется — оно в PLAN.md).

## 6. Риски дизайна

| Риск | Митигация |
|---|---|
| Ввод Заказчика не доходит до живой делегации | Эскалации пакетно в точках пауз; срочный стоп relay выполняет сам (kill delegate + запись в active_sessions + PLAN) |
| ПМ-сабагент деградирует (J1-проблема в новом месте) | Контекст восстанавливается с холодного старта (промпт п. «Вход»); потери = только незаписанное; пинг relay (§5) |
| relay втягивается обратно в оркестрацию (ротация ролей незаметна) | §4 — явный анти-паттерн; ретро-триггер J4 проверяет «что делает relay» при первом же прогоне |
| Двойное владение push | Пушит только ПМ-сабагент; relay пуш запрещен технически — нет необходимости, у relay нет задач на репо |
