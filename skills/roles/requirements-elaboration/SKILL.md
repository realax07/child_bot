# Выработка требований

Как превратить разговор с Заказчиком в проверяемый документ требований. База: IEEE 830/29148, MoSCoW.

## Когда применять

- Проект или крупная фича не имеют `requirements.md`
- Требования есть, но содержат оценки без критериев («быстро», «удобно»)
- Заказчик просит «сформулировать ТЗ»

Не применять для: архитектуры и стека (это системный анализ), тест-кейсов (это QA).
Предварительная фаза — скилл `brainstorming` (замысел до формулировок).

## Процедура

1. **Собери интент.** Один вопрос: какую проблему решает система и для кого. Не уходи в функции, пока не зафиксирована ценность — функции без ценности порождают лишнюю разработку. (Замысел не ясен — скилл `brainstorming`.)
2. **Перечисли функции.** Формулировки со стороны пользователя: «пользователь может X». Глагол действия + объект + результат. Проверяй каждую: если нельзя назвать пользователя, который это заметит — это не функция, а реализация.
3. **Пронумеруй — нумерационный преемник (J45).** `FR-N`/`NFR-N` сквозно по проекту: нумерация продолжает последний известный идентификатор. Источники: master-specs `openspec/specs/` (максимальный FR/NFR), архивные ТЗ (`docs/ba/`, archive-пакеты), предыдущий requirements.md. Дубль идентификатора между пакетами ломает трассировку так же, как дубль внутри файла.
4. **Проверь каждое требование на качество.** Атомарное (одно «должно» на требование), однозначное (два читателя поймут одинаково), проверяемое (можно написать тест). Критерии качества — контракт 1 (`contracts/artifact_contract.md`), здесь не дублируются.
5. **Приоритизируй MoSCoW.** Must — без этого релиз бессмыслен; Should — важно, но есть обход; Could — приятно. Расставляй вместе с Заказчиком: приоритет, назначенный без него, будет оспорен на приемке.
6. **Собери НФТ.** Производительность, безопасность, доступность, совместимость. Каждое — с измеримым порогом. НФТ без числа непроверяемо и потому бесполезно.
7. **Зафиксируй ограничения и открытые вопросы.** Недоговоренности — в раздел «Открытые вопросы» с пометкой, кто решает. Скрытая недоговоренность всплывет на приемке в худшей форме.
8. **Разбери утверждение Заказчика на директивы (J45).** «Утверждаю» редко бывает только утверждением: текст после него («не забывай, что нам нужны мокапы») — обязательные ограничения/требования пакета. Каждая директива → отдельная строка ограничений или FR со ссылкой на дословную цитату. Молчаливое проглатывание директивы = требование, которого нет в ТЗ.
9. **Покажи черновик Заказчику** малыми итерациями после каждого раунда. Правка требований в начале стоит минуты, на приемке — недели.

## Жизненный цикл requirements.md (J45)

Файл в корне репозитория — ТЗ **активного** пакета. При архивации пакета
требования переезжают в `docs/ba/requirements-<change-id>.md` (история, не
удаляются), а корневой файл становится ТЗ следующего пакета. Нумерация FR/NFR
— сквозная через эти переезды (см. п.3).

## Формат результата

Структура `requirements.md`: Общее описание → Аудитория → FR → NFR → Приоритеты → Ограничения → Открытые вопросы. Формат и условия контракта: `contracts/artifact_contract.md` (контракт 1 — источник правды по качеству и статусной модели; этот скилл их не дублирует).

## Пример

**Плохо:** «Система должна быстро искать по страницам».
**Хорошо:** «FR-3: Пользователь получает результаты поиска по подстроке заголовка за < 500 мс на corpus до 10 000 страниц».

## Инструмент (scripts/)

**`scripts/numbering_registry.py`** — реестр нумерации FR/NFR/US/TC/SC:
занятые номера, max N по префиксу, пропуски, дубликаты. Использовать при
продолжении нумерации (не выдумывать номера — брать max+1) и при ревью
(дубликат = дефект нумерации).

```bash
python skills/requirements-elaboration/scripts/numbering_registry.py openspec/ docs/ba/
python skills/requirements-elaboration/scripts/numbering_registry.py openspec/add-wiki/specs/ --prefix FR
```

Exit-коды: 0 — чисто; 2 — дубликаты (разобрать до выдачи ТЗ).

## Ошибки

- Требование-фича «на вырост» без Must-приоритета — мусор в скоупе.
- Решения реализации в ТЗ («React», «PostgreSQL») — забирают у системного анализа свободу выбора.
- Требования от лица системы («система должна хранить») вместо пользователя — проверять нечем.
