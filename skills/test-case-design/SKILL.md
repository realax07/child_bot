# Проектирование тест-кейсов

Как из спеки получить полный трассируемый набор проверок и тест-кейсов. Основа: техники test design (эквивалентное разбиение, граничные значения, негативные классы).

## Когда применять

- Есть change-пакет OpenSpec, нужны тест-кейсы в `test-model/new/` (чеклист CHK — внутренний рабочий шаг, НЕ артефакт: J23, 2026-10-12)
- Оценка полноты существующего набора кейсов

Не применять для: написания автотестов (это автоматизация), ревью (это роль ревьюера).

## Процедура

1. **Инвентаризация.** Выпиши все Requirements и Scenario из спеки change-пакета. Каждый Scenario — кандидат в пункт чеклиста.
2. **Техники дополнения.** Для каждого требования — по порядку:
   - **классы эквивалентности** сначала: разбей каждый вход на классы (валидные и невалидные), по одному представителю из класса в кейс;
   - **граничные значения МЕЖДУ классами**: пустая строка, 1 символ, максимум, максимум+1 (граница без класса — магия; сначала классы, потом их края);
   - **негативные классы**: невалидный тип, отсутствующее поле, чужой ресурс (403), повторное действие;
   - **состояния**: действие на несуществующем объекте, повторная операция, операция после удаления;
   - **комбинации**: зависящие друг от друга правила → таблица решений; независимые многопараметрические наборы → pairwise (references/decision-tables-pairwise.md).
   Типовые баги живут на границах и в комбинациях, не в середине классов — поэтому п.2 обязателен, а не «по желанию».
3. **API-эндпоинты — матрицы.** Для каждого нового/измененного эндпоинта прогони auth-матрицу (включая «токен удаленного пользователя») и input-validation матрицу — references/api-matrices.md. Это базис, поверх него классы и комбинации.
4. **Составь внутренний чеклист** (рабочий инструмент, в репозиторий НЕ кладется): `источник (Requirement + FR-N) | проверка | тип (поз/нег/гран/НФТ) | приоритет`. Приоритет наследуй от MoSCoW источника.
5. **Проверь покрытие.** Каждый Requirement ≥ 1 пункта; каждый Scenario ≥ 1 пункта; у каждого пункта есть источник. Непокрытый Must — блокер набора.
6. **Разверни в тест-кейсы.** Каждый пункт → кейс `TC-<domain>-NNN` с трассировкой к Requirement + Scenario (поле «источник» в шапке кейса): предусловия, атомарные шаги, ожидаемый результат, конкретные тестовые данные. «Валидный пользователь» — не данные; `user: test_user_1 / Corr3ct_Pass!` — данные.
7. **Положи в `test-model/new/<change-id>/`** — по файлу на домен. Путь имеет процессный смысл: только там их увидит ревьюер.

## Ожидаемый результат

Проверяемый без знания кода: HTTP-код, тело ответа, элемент UI, состояние БД. «Работает корректно» — не ожидаемый результат, а отказ от проверки.

## Инструменты (scripts/ + references/)

**`scripts/coverage_matrix.py`** — матрица «сценарии спеки ↔ кейсы»: сценарии
без кейсов (пробелы) и кейсы-сироты (нет ссылки SC/FR/NFR). Прогон перед
сдачей кейсов — пробелы недопустимы (трассировка TC → Req/Scenario, J23).

```bash
python skills/test-case-design/scripts/coverage_matrix.py openspec/changes/<change>/ --cases test-model/new
```

**`references/negative-classes.md`** — каталог классов тест-дизайна
(эквивалентность, границы, негативные, состояния, authz, конкурентность).
Прогонять кейс-план по каталогу: неприменимый класс помечать «N/A
(основание)», не молчать.

**`references/decision-tables-pairwise.md`** — таблицы решений (правила
«если…то…» с несколькими условиями) и pairwise (многопараметрические
наборы: полный перебор 120 → 10–25 кейсов без потери парного покрытия).

**`references/api-matrices.md`** — auth-матрица (7 строк, включая «токен
удаленного пользователя → 401») и input-validation матрица (11 строк:
пустое тело, пропуски полей по одному, типы, границы, null, инъекции,
дубликаты) — обязательный базис на каждый эндпоинт.

## Ошибки

- Кейс объединяет два пункта чеклиста — падение одного делает результат второго нечитаемым.
- Тестовые данные описаны, а не приведены — кейс невоспроизводим.
- Негативный кейс без ожидаемой ошибки — проверка превращается в «не упало, и ладно».
- Пункт без источника — трассировка разорвана, при изменении спеки кейс останется незамеченным.
