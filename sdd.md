## 1. Стек и обоснование

Ограничения: персональный бот на одного пользователя, всё локально на нашем
сервере (решения №6, №7), без внешних сервисов и аналитики.

| Слой | Выбор | Обоснование |
|---|---|---|
| Bot-фреймворк | **python-telegram-bot v21+ (async)**, long polling | Назван в ТЗ §8; для одного пользователя polling проще вебхука (не нужен TLS-эндпоинт) |
| БД | **SQLite**, `journal_mode=WAL`, `foreign_keys=ON`, файл вне репозитория | ТЗ §8; ноль демонов, бэкап = копия файла; WAL покрывает запись одного пользователя с запасом |
| Время | Хранение в UTC (`DATETIME`), TZ пользователя через **zoneinfo** (IANA-имя в `users.timezone`) | Однозначность при DST/смене пояса; локальное время только на границах ввода/вывода |
| Планировщик | **APScheduler** в процессе — НЕ подключен в Пакете 1 | Пакет 2 (автонапоминания); в Пакете 1 фазы диалога — `context.user_data` PTB, один процесс |
| Развертывание | docker compose на нашем сервере рядом с wiki (решение №7) | Инфраструктура уже есть; выкатка — отдельный этап после dev/QA |

## 2. Компоненты

```
Telegram ⇄ long polling → Application (PTB v21) [src/main.py]
  ├── handlers/  — только Telegram-протокол: start, events, backfill, undo, common
  ├── services/  — вся бизнес-логика (чистые функции/классы):
  │     state (состояние из последнего события), event (запись/конфликты),
  │     calculation (разметка день/ночь, склейка, страницы дня),
  │     settings (13 ключей), access (роль observer)
  ├── repositories/ — единственная точка доступа к БД: users, sleep_events, settings
  ├── texts.py   — тексты ТЗ §7 дословно
  └── db.py      — схема v1, WAL
```

Правило слоёв (FR-1): handlers не импортируют repositories; расчёты — на лету
из сырых событий, агрегаты не хранятся (ТЗ §9.5).

## 3. Модель данных

- `users`: telegram_id, timezone, role (`parent`|`observer`, дефолт `parent` — решение №5).
- `sleep_events`: user_id, event_type (`sleep`|`wake`), timestamp (UTC),
  created_at, is_backfilled, sleep_type (`day`|`night`|null), is_merged.
- `settings`: user_id, key, value — 13 ключей (12 ТЗ §5 + `target_nap_duration`=90 мин, решение №1).
- `settings_history` и `daily_summary` НЕ создаются (Пакеты 2–3).

## 4. Ключевые алгоритмы (детали — design.md пакета)

- Разметка: ночь ⇔ начало ≥ 19:00 ИЛИ конец ≤ 07:00; предупреждение при начале в [18:50; 19:00); метка requires_check при ночном сне < 40 мин (только данные).
- Страница дня: 06:00 → 05:59 следующих суток; ночь целиком относится к дню начала сна (решение №2).
- Склейка: бодрствование между смежными снами < порога (`merge_threshold`, 20 мин) → интервалы объединяются при расчёте.
- Конфликты задним числом: пересечение/нарушение порядка → §7.13; «Изменить» = атомарная перезапись целевой записи (решение №1).

## 5. Приватность и эксплуатация

БД и бэкапы (`sqlite3 .backup`) только локально на нашем сервере; исходящий
HTTP из обработчиков запрещен; логи без содержимого сообщений (user_id + тип
события). Токен бота — env, вне репозитория.
