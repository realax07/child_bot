# Каталог классов тест-дизайна (reference для test-case-design)

Классы, из которых собираются кейсы. На каждый класс — минимум один кейс,
если он применим к требованию. Трассировка TC → Req/Scenario обязательна
(контракт qa_case_author, J23).

## 1. Классы эквивалентности (positive)

- Валидное значение из каждого класса входа (для диапазона 1–100: одно значение из класса, не 1 и не 100).
- Типовой happy-path сценария спеки — по одному кейсу на сценарий, не «всё в одном».

## 2. Граничные значения (boundaries)

- Для числовых диапазонов: min, min-1, min+1, max, max+1.
- Для длин строк/списков: 0, 1, предел, предел+1.
- Для дат/времен: смена суток, конец месяца, високосный год, часовой пояс (если применимо).

## 3. Негативные классы (negative)

- Пустой ввод / отсутствие обязательного поля.
- Невалидный тип/формат (строка вместо числа, битый JSON, невалидный email).
- Выход за диапазон (вверх и вниз).
- Дубликат (повторное создание существующего).
- SQL/HTML/JS-инъекции в текстовых полях (для sanitize-поверхности).
- Превышение лимитов размера (большой файл/строка).

## 4. Состояния и переходы (state)

- Каждый переход конечного автомата (черновик → опубликована → архив) — отдельный кейс.
- Недопустимый переход из текущего состояния (архив → редактирование) — негативный.
- Действие в отсутствии обязательного предшествующего действия.

## 5. Авторизация/изоляция (authz)

- Действие без аутентификации (302/401).
- Действие под пользователем без прав (403).
- Изоляция данных: пользователь A не видит/не меняет данные пользователя B.
- Прямой URL/API-вызов в обход UI (не только клик по скрытой кнопке).

## 6. Конкурентность/повторы (только если затронуто требованием)

- Двойной сабмит формы (double-click, повторный POST).
- Параллельное изменение одной записи двумя сессиями.

## Правило полноты

Кейс не «на все классы сразу»: один кейс = один класс/сценарий.
Если класс не применим — фиксируется в кейс-файле строкой «класс X — N/A
(основание)», а не молча пропускается.
