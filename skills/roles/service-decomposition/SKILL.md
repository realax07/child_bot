# Декомпозиция сервисов и швы делегаций

Как резать систему на сервисы и пакет — на задачи-делегации. Эмпирия
ekotov-wiki: search (выделен), images (выделен), backup (sidecar), netdata
(наблюдение), auth (отказ выделения с аргументами). Не истина — рабочие
эмпирические правила проекта; спорные случаи — research.md + Заказчик.

## Когда применять

- СА: нарезка change-пакета на задачи и «Рекомендации к нарезке» (швы)
- СА: решение «сервис vs роутер в монолите» (в research.md — обязательно)
- dev_lead: консолидация параллельных задач, обнаружение пересечений

Не применять для: выделения роли-сабагента (это критерии AGENTS.md
«выделить сабагента»), разбиения спеки на домены (openspec-authoring п.2 —
домены спеки ≠ сервисы).

## 1. Граница сервиса: когда выделять

Выделяй сервис ТОЛЬКО при ≥1 сильном критерии:

| Критерий | Прецедент |
|---|---|
| Отдельный том данных вне БД ядра (файлы, индексы) | images: том images-data, файлы не в wiki-data |
| Свой профиль доступа к БД (RO-реплика / RW-своей-схемы) | search: RO; images: RW своей схемы |
| Независимый цикл масштабирования/деградации (503 управляемая) | search: nginx отдаёт 503 при недоступности — ядро живо |
| Отдельный цикл деплоя без остановки ядра | images/search деплоятся по тегам независимо |

НЕ выделяй при:
- Сетевой хоп на каждый запрос при N пользователей ~2 без выигрыша (auth:
  сессии в общей БД, middleware в каждом запросе — решение «не выделять»)
- «Так красивее» без эксплуатационного критерия — монолит + границы модулей
- Сервис нужен «потом» — YAGNI: границу оставь в карте (J44), код — в ядре

## 2. Владение схемой БД (межсервисное)

- **Владелец схемы — ровно один сервис.** gallery-таблицы принадлежат images:
  ядро НЕ пишет в них (первичное создание — миграцией ядра по запросу
  владельца, владение не меняется).
- **Профили доступа**: RO (search: read-only URI + fallback immutable, нюансы
  WAL — в db.py сервиса) / RW-своей-схемы (images) / RW-общей (ядро).
- **Чужие таблицы — через API владельца**, не через SQL: иначе откат сервиса
  ломает ядро.
- Миграции схем сервисов — в контейнере владельца, не в ядре
  (migrate_gallery паттерн: ядро создает пустую схему, владелец накатывает).

## 3. Сквозные процессы (cross-service) — специальная нарезка

Сквозной процесс = пользовательский сценарий, проходящий ≥2 сервисов
(например «загрузка аватара»: nginx → images → том; «поиск»: nginx → search →
RO БД; «деплой»: deploy.sh → registry → compose → миграция → healthcheck).

Правила нарезки сквозных процессов:

1. **Один владелец сценария** в tasks.md — задача «сквозной смоук процесса X»
   существует, даже если каждый сегмент уже покрыт юнитами. Сегментные тесты
   НЕ заменяют сквозные (прецедент DEF-002: статика жива в ядре, сломана в
   nginx-слое доставки).
2. **Контракт на стыке — в спецификации обоих сервисов**: заголовки
   (X-Service), коды деградации (503 vs 502), таймауты. Нестыковка контрактов
   = дефект спецификации, не кода.
3. **Деградация проектируется, не случается**: для каждого сквозного процесса
   укажи в design — что видит пользователь при недоступности сегмента
   (search: 503 от nginx, управляемая; images: 503; backup: не влияет на
   пользователей).
4. **Наблюдаемость сквозная**: X-Service заголовок / логи каждого сегмента —
   иначе отладка = археология по трем контейнерам.
5. **Миграции на сквозном шве**: порядок «миграция владельца до старта
   потребителя» — в deploy-скрипт явно (deploy.sh: one-shot миграция до up).
6. **Тестирование сквозного процесса — этап QA (решение Заказчика
   2026-10-12)**: SA не создает отдельную dev-задачу «сквозной смоук» — он
   (а) специфицирует процесс и деградацию в design, (б) включает сквозной
   набор в «План тестовых прогонов» пакета (набор «смок» = отдельная
   QA-делегация-раннер против compose-стенда/прода). Сегментные юниты
   остаются у dev; сквозная верификация — у QA.

## 4. Швы делегаций (нарезка пакета на задачи-сабагенты)

Единица резки — **зона файлов** (непересекающиеся пути), не «тема»:

1. **Шов = непересекающиеся зоны записи.** Две задачи с общим файлом — это
   одна задача или последовательные. Общая зона = «НЕЛЬЗЯ делить» — явно в
   «Рекомендации к нарезке». Сквозной процесс — НЕ резать на dev-задачи:
   его верификация уходит на QA-этап (см. §3 п.6), SA фиксирует только
   сегментные задачи + вход в план прогонов.
2. **[P]-маркер** — только для задач с доказанно непересекающимися зонами
   (каждая в своем worktree); пересечение = коллизия worktree (прецедент
   затирания WIP 3.2/4.1).
3. **Порядок по зависимостям**: данные/миграции → API → UI → полировка;
   сквозной смоук — ПОСЛЕДНЕЙ задачей пакета.
4. **[M] с ≥2 под-областями → [S]+[S]**: реализация отдельно, тест-файл
   отдельной делегацией с готовым кодом (J21/J31: 160-минутные обрывы на
   циклической отладке).
5. **Каждая задача несет**: типы работ ([code]/[tests]/[docs]/[infra]/
   [migration]/[design]), точные пути, критерий проверки, трассировку.
6. **План прогонов по наборам** (api / web-mobile / web-desktop / смоук):
   каждый набор = отдельная делегация-раннер; SA нарезает здесь, ПМ не
   импровизирует.

## 5. Чек-лист СА перед нарезкой пакета

- [ ] Для каждого «сервис?» решения — критерий §1 в research.md (или «не выделять» с основанием)
- [ ] Владелец каждой новой таблицы/тома назван явно (§2)
- [ ] Сквозные процессы перечислены; у каждого — владелец, контракты стыков, деградация, сквозной смоук-кейс (§3)
- [ ] Зоны задач не пересекаются; [P] обоснован (§4)
- [ ] Порядок миграций на межсервисных швах — в deploy-план
- [ ] «Рекомендации к нарезке» заполнены (швы, НЕЛЬЗЯ делить, [P], прогоны)

## 6. Паттерн-эталон (сверка с индустрией, senior-architect)

Наш масштаб (1–3 разработчика, ОГР-1) — **modular monolith**: сервис выделяется
только при критериях §1 (разный масштабирование-цикл, независимый деплой,
строгая изоляция данных) — что совпадает с индустриальной матрицей
(1–3 разработчика → modular monolith; extract service при: сильно отличающиеся
потребности масштабирования, независимый деплой, технологические ограничения).
Строгая изоляция данных при выделении — обязательна (отдельная БД/том), общая
БД допустима только в монолите. Спорный случай → research.md с trade-off +
Заказчик. ADR на решение (architecture/adr/).

## Ошибки

- Сервис «про запас» без эксплуатационного критерия — лишний хоп и деплой-цикл.
- Два писателя в одну схему — рассинхрон миграций гарантирован.
- Сквозной процесс без сквозного смоука — сегменты зеленые, процесс сломан.
- Задачи «по темам» с общей зоной — коллизии worktree и затертый WIP.
## Инструмент (scripts/)

**`scripts/seam_checker.py`** — проверка «зоны задач не пересекаются» (§4):
подать зоны из tasks.md в формате `ID:путь`, скрипт ищет пересечения
префиксов путей.

```bash
python skills/service-decomposition/scripts/seam_checker.py T1:backend/app/wiki.py T2:backend/app/pages.py
python skills/service-decomposition/scripts/seam_checker.py T1:backend/ T2:backend/app/wiki.py --strict
```

Exit-коды: 0 — швы чистые; 1 — пересечения (пере-нарезать или явная
[P]-параллель с договоренностью о порядке коммитов); 2 — то же для CI.

- Деградация «сама получится» — 502 вместо управляемой 503 в бою.
