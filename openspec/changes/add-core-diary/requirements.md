## 1. Назначение пакета

Ядро дневника сна: родитель отмечает «😴 Заснул» / «☀️ Проснулся» (в том числе задним числом), бот хранит сырые события, размечает день/ночь (19:00–07:00), склеивает короткие пробуждения (порог 20 мин), отменяет последнюю отметку и показывает подтверждения. Без расчёта окон сна и автонапоминаний (Пакет 2), без UI настроек, истории и /help (Пакет 3).

Тексты ответов бота заданы в ТЗ §7 и в требованиях не дублируются — требования ссылаются на разделы.

## 2. Требования

### Группа A. Каркас и хранение данных

#### FR-1: Слоистая архитектура
Система MUST быть разделена на слои handlers → services → repositories; обработчики Telegram (handlers) NOT MUST обращаться к хранилищу напрямую — только через сервисы; бизнес-логика (разметка, склейка, расчёты) MUST быть отделена от интерфейса (ТЗ §8, §10.1).

##### Scenario: Разделение слоёв
- WHEN реализуется новое поведение дневника (событие, разметка, склейка)
- THEN логика вычислений находится в service-слое и вызывается из handler'ов, доступ к БД — только через repositories

#### FR-2: База данных
Система MUST использовать SQLite в режиме WAL со схемой из трёх таблиц: `users`, `sleep_events`, `settings` (ТЗ §9.1–9.3; решения 26.10 №7 — данные только на нашем сервере).

##### Scenario: Инициализация БД
- WHEN бот запускается первый раз (БД отсутствует)
- THEN создаются таблицы `users`, `sleep_events`, `settings` в соответствии с ТЗ §9.1–9.3, включён WAL

#### FR-3: Хранение сырых событий
`sleep_events` MUST хранить сырые события (event_type sleep/wake, фактический timestamp, created_at, is_backfilled, sleep_type, is_merged — ТЗ §9.2). Разметка день/ночь, склейка и суммарные показатели MUST вычисляться на лету из сырых событий, а не храниться заранее (ТЗ §9.5). Колонки `sleep_type` и `is_merged` (ТЗ §9.2) — резерв схемы: при записи события они не вычисляются и заполняются NULL; `sleep_type` — результат разметки, вычисляемой при чтении/расчёте (зависит от конца интервала, длительности и настроек).

##### Scenario: Событие фиксируется как есть
- WHEN родитель отмечает любое событие (кнопкой или задним числом)
- THEN в `sleep_events` появляется запись с фактическим временем события и признаком способа ввода; никакие вычисленные агрегаты в запись не пишутся

##### Scenario: sleep_type при записи не вычисляется
- WHEN родитель нажал «😴 Заснул», затем «🕐 Сейчас» (конец интервала неизвестен)
- THEN запись события содержит sleep_type = NULL; разметка day/night вычисляется при чтении/расчёте

#### FR-4: Часовой пояс
При `/start` часовой пояс пользователя MUST сохраняться в `users.timezone` из TG-профиля (первое приближение, ТЗ §8.2), и все ввод/вывод/разметка времени MUST выполняться в этом поясе.

##### Scenario: Время в поясе пользователя
- WHEN пользователь с сохранённым часовым поясом отмечает «😴 Заснул» в 22:10 по своему локальному времени
- THEN событие сохранено как 22:10 пояса пользователя, разметка день/ночь выполнена по локальному времени пользователя

---

### Группа B. Команда /start

#### FR-5: Инициализация пользователя
Команда `/start` MUST: создать пользователя в `users` (при первом обращении), сохранить часовой пояс (FR-4), создать 13 дефолтных настроек (FR-11), установить состояние «бодрствует» и отправить текст ТЗ §7.1. При повторном `/start` повторная инициализация настроек NOT MUST происходить.

##### Scenario: Первый запуск
- WHEN новый пользователь отправляет `/start`
- THEN бот отвечает текстом §7.1, пользователь и его дефолтные настройки созданы, меню показывает «😴 Заснул»

##### Scenario: Повторный запуск
- WHEN существующий пользователь отправляет `/start`
- THEN бот отвечает текстом §7.1, настройки и события пользователя не сбрасываются

---

### Группа C. Кнопки «😴 Заснул» / «☀️ Проснулся»

#### FR-6: Динамическое меню по состоянию
Главное меню MUST зависеть от состояния ребёнка: бодрствует → «😴 Заснул», спит → «☀️ Проснулся» (ТЗ §4.1, §6). Нажатие кнопки, противоречащей состоянию, MUST быть невозможно (кнопка отсутствует в актуальном меню). Состояние ребёнка выводится из последнего события, а не хранится отдельно. Обработчик колбэка MUST перепроверять состояние по БД перед созданием события: нажатие устаревшей кнопки из старого сообщения, противоречащее актуальному состоянию, MUST игнорироваться с перерисовкой актуальной клавиатуры.

##### Scenario: После /start
- WHEN ребёнок считается бодрствующим
- THEN меню содержит «😴 Заснул» и не содержит «☀️ Проснулся»

##### Scenario: Переключение
- WHEN родитель нажал «😴 Заснул»
- THEN следующее меню содержит «☀️ Проснулся» и не содержит «😴 Заснул»

##### Scenario: Устаревшая кнопка из истории чата
- WHEN ребёнок спит и родитель нажал «😴 Заснул» в устаревшей клавиатуре предыдущего сообщения
- THEN событие не создано, клавиатура перерисована в актуальное состояние («☀️ Проснулся»)

#### FR-7: Отметка засыпания
Нажатие «😴 Заснул» MUST предлагать выбор времени (FR-14: «🕐 Сейчас» / «⏪ Ввести время вручную», ТЗ §7.10). При выборе «Сейчас» система MUST создать событие sleep с текущим временем, переключить меню (FR-6) и ответить текстом ТЗ §7.5; строка «Крайнее пробуждение: …» берётся из настройки «Крайнее время пробуждения от дневного сна» (§5).

##### Scenario: Засыпание сейчас
- WHEN ребёнок бодрствует и родитель нажал «😴 Заснул», затем «🕐 Сейчас»
- THEN создано событие sleep, меню переключилось на «☀️ Проснулся», ответ — §7.5 с фактическим временем засыпания

#### FR-8: Отметка пробуждения
Нажатие «☀️ Проснулся» MUST предлагать выбор времени (FR-14). При выборе «Сейчас» система MUST создать событие wake, переключить меню и ответить текстом ТЗ §7.2. Строки с окном дневного сна в §7.2–7.4 в этом пакете NOT MUST выводиться (окна — Пакет 2).

##### Scenario: Пробуждение сейчас
- WHEN ребёнок спит и родитель нажал «☀️ Проснулся», затем «🕐 Сейчас»
- THEN создано событие wake, меню переключилось на «😴 Заснул», ответ — подтверждающая строка §7.2 («✅ Пробуждение записано в ЧЧ:ММ.») без строки окна

### Группа D. Разметка день/ночь

#### FR-9: Границы ночного сна
Сон MUST размечаться как ночной, если его начало ≥ 19:00 или конец ≤ 07:00 (настройка «Границы ночного сна», дефолт 19:00–07:00); иначе — как дневной (ТЗ §4.2).

##### Scenario: Ночной сон
- WHEN интервал сна 22:10 → 07:20
- THEN интервал размечен как ночной

##### Scenario: Дневной сон
- WHEN интервал сна 13:30 → 15:05
- THEN интервал размечен как дневной

#### FR-10: Поздний дневной сон
Сон с началом до 19:00, но позднее (граница − предупреждаемый зазор), вблизи ночной границы (например, 18:50) MUST размечаться как дневной с предупреждением «Поздний дневной сон может сдвинуть ночной» (ТЗ §4.2, ответ после записи события).

##### Scenario: Сон в 18:50
- WHEN создан сон с началом 18:50
- THEN сон размечен как дневной и бот выводит предупреждение §4.2

#### FR-11: Короткий сон у ночной границы
Сон с началом в ночном диапазоне (например, 19:30) длительностью меньше 40 минут MUST получать в данных метку «требует проверки» (ТЗ §4.2). Вывод текста по этой метке NOT MUST выполняться в этом пакете (Пакет 2).

##### Scenario: Сон 19:30 длиной 30 минут
- WHEN создан интервал 19:30 → 20:00
- THEN интервал размечен ночным и помечен «требует проверки» в данных; в ответе бота дополнительного текста нет

#### FR-12: Отнесение сна к странице дня момента начала
Сон MUST целиком относиться к странице дня, в которую попадает момент НАЧАЛА сна; страница дня = 06:00 текущего дня → 05:59 следующего (`day_start` из настроек, ТЗ §5 «Начало дня 06:00»). Для сна с началом в [00:00; 06:00) это страница предыдущего календарного дня (решение ПМ 26.10, согласовано с «ночь за вчера» — решение продакта №2); ночной сон, переходящий через полночь, вследствие этого относится к странице дня начала сна.

##### Scenario: Ночь через полночь
- WHEN записан сон 22:10 (10 октября) → 07:20 (11 октября)
- THEN весь интервал отнесён к дню 10 октября

##### Scenario: Сон с началом до 06:00
- WHEN записан сон с началом в [00:00; 06:00), например 02:00 → 05:30
- THEN интервал отнесён к странице предыдущего календарного дня (страница дня 06:00–05:59)

### Группа E. Склейка снов

#### FR-13: Автосклейка коротких пробуждений
Пробуждение короче порога склейки MUST не разрывать сон: смежные интервалы объединяются в один сон, короткое пробуждение не создаёт отдельного периода бодрствования (ТЗ §4.3). Расчёт — на лету (FR-3).

##### Scenario: Склейка
- WHEN записаны интервалы: сон 13:00 → 14:00, бодрствование 14:00 → 14:15, сон 14:15 → 15:00, порог 20 мин
- THEN расчётные интервалы сна: один сон 13:00 → 15:00, бодрствование за период не учитывается

##### Scenario: Пробуждение длиннее порога
- WHEN пробуждение между двумя снами длится 25 мин при пороге 20 мин
- THEN интервалы NOT MUST склеиваться: два отдельных сна и период бодрствования 25 мин

#### FR-14: Порог из настроек
Порог склейки MUST браться из `settings` пользователя (дефолт 20 мин, ТЗ §5); изменение порога меняет результат склейки при следующем расчёте без перезаписи событий.

##### Scenario: Порог из settings
- WHEN у пользователя порог склейки установлен 30 мин и записано пробуждение 25 мин
- THEN смежные сны склеены

---

### Группа F. Ввод задним числом

#### FR-15: Выбор времени после события
После нажатия «😴 Заснул» / «☀️ Проснулся» бот MUST предлагать «🕐 Сейчас» / «⏪ Ввести время вручную» (ТЗ §4.4, §7.10). Выбор «Ввести время вручную» MUST запросить время текстом §7.11.

##### Scenario: Диалог ввода
- WHEN родитель нажал кнопку события
- THEN бот показывает §7.10 с кнопками «🕐 Сейчас» и «⏪ Ввести время вручную»

#### FR-16: Форматы времени
Ручной ввод MUST принимать форматы `10:50` (сегодня), `вчера 22:30`, `08.10 7:15` (ТЗ §4.4). Нераспознанный ввод MUST вызывать ответ §7.12 с повторным запросом без создания события.

##### Scenario: Корректный ввод
- WHEN родитель вводит «вчера 22:30»
- THEN событие создано на 22:30 предыдущего календарного дня с признаком is_backfilled

##### Scenario: Ошибка формата
- WHEN родитель вводит «завтра 10:00» / произвольный текст
- THEN событие не создано, бот отвечает §7.12 и снова ждёт время

#### FR-17: Глубина ввода 3 дня
Событие старше 3 дней (настройка «Максимальная глубина ввода», ТЗ §5) MUST отклоняться ответом §7.15 без создания записи.

##### Scenario: Слишком давно
- WHEN родитель вводит время 4 дня назад
- THEN запись не создана, бот отвечает §7.15

#### FR-18: Конфликты
Ввод, конфликтующий с уже записанными событиями (пересечение по времени или нарушение порядка sleep/wake), MUST вызывать ответ §7.13 с кнопками [Изменить] / [Отменить] (ТЗ §4.4, §7.13). «Изменить» перезаписывает целевое существующее событие с уведомлением (рекомендация ОВ-ПО-1 — см. §3 Открытые вопросы); «Отменить» не меняет данные.

##### Scenario: Конфликт и «Изменить»
- WHEN записано «Проснулся» в 13:30 и родитель вводит задним числом «Заснул» на 13:30
- THEN бот показывает §7.13; после «Изменить» целевое событие перезаписано, данных-дубликатов нет

##### Scenario: Конфликт и «Отменить»
- WHEN в диалоге §7.13 выбрано «Отменить»
- THEN существующие события не изменены, новое событие не создано

#### FR-19: Успешный ввод — сводка без окон
После успешного ввода задним числом бот MUST отвечать текстом §7.14 с обновлённой сводкой за день, где в этом пакете указываются только суммарные сон и бодрствование; строки окон NOT MUST выводиться (окна — Пакет 2, interpretation note брифа AC-4).

##### Scenario: Сводка после ввода
- WHEN родитель успешно ввёл событие задним числом
- THEN бот отвечает §7.14: подтверждающая строка с временем и суммарные сон/бодрствование за день, без упоминания окон

#### FR-20: «Вчера» — календарный день
Значение «вчера» в ручном вводе MUST означать прошедший календарный день (00:00–23:59 локального времени пользователя), а не «24 часа назад» (решения 26.10 №4). Если разрешённое время оказывается в будущем относительно момента ввода, ввод MUST отклоняться с предупреждением.

##### Scenario: Вчера поздно вечером
- WHEN сейчас 08:00 10 октября и родитель вводит «вчера 22:30»
- THEN событие создано на 22:30 9 октября

##### Scenario: Спорное время
- WHEN разрешённое «вчера ЧЧ:ММ» даёт момент в будущем относительно текущего момента
- THEN событие не создано, бот выводит предупреждение о некорректном времени

### Группа G. Кнопка «↩️ Отменить последнее»

#### FR-21: Отмена последней отметки
Кнопка «↩️ Отменить последнее» MUST присутствовать в меню и отменять последнюю отметку события: запись удаляется из `sleep_events`, состояние ребёнка и меню возвращаются к состоянию до отметки (решения 26.10 №3). Отмена NOT MUST удалять более ранние события.

##### Scenario: Отмена засыпания
- WHEN последнее событие — «😴 Заснул» в 13:30 и родитель нажал «↩️ Отменить последнее»
- THEN запись удалена, ребёнок снова считается бодрствующим, меню показывает «😴 Заснул»

##### Scenario: Нечего отменять
- WHEN событий у пользователя нет и родитель нажал «↩️ Отменить последнее»
- THEN данные не изменены, бот сообщает, что отменять нечего

---

### Группа H. Роль «наблюдатель»

#### FR-22: Наблюдатель — только чтение
Схема `users` MUST содержать поле роли (`parent` — дефолт, `observer` — решение 26.10 №5). Пользователь с ролью `observer` MUST иметь доступ к просмотру сводок (механизмы сводок появляются в пакетах 2–3) и NOT MUST иметь возможность создавать события: нажатие кнопок событий «😴 Заснул» / «☀️ Проснулся» / «↩️ Отменить последнее» игнорируется с сообщением, что отметки недоступны. UI назначения роли NOT MUST входить в этот пакет.

##### Scenario: Наблюдатель жмёт кнопку события
- WHEN пользователь с ролью `observer` нажимает «😴 Заснул»
- THEN событие не создано, бот сообщает о недоступности отметок

##### Scenario: Наблюдатель запрашивает данные
- WHEN пользователь с ролью `observer` обращается за сводкой за день
- THEN сводка показывается так же, как родителю (по мере появления механизмов сводок в пакетах 2–3)

---

### Группа I. Настройки как данные

#### FR-23: Дефолтные настройки
При `/start` MUST создаваться 13 параметров со значениями по умолчанию (ТЗ §5 + решение 26.10 №1): 12 параметров ТЗ (мин./макс. бодрствование до дневного сна 5:20/6:00, крайнее пробуждение 15:30, целевой уход 22:00, крайний уход 22:30, границы бодрствования 12,0/12,5 ч, напоминание заранее 15 мин, начало дня 06:00, порог склейки 20 мин, границы ночи 19:00–07:00, глубина ввода 3 дня) плюс новая настройка «целевая длительность дневного сна» = 1 ч 30 мин.

##### Scenario: Создание дефолтов
- WHEN новый пользователь прошёл `/start`
- THEN в `settings` для его user_id существуют все 13 параметров со значениями по умолчанию

#### FR-24: Хранение и чтение настроек
Настройки MUST храниться в `settings` на каждого пользователя (ключ user_id, ТЗ §5, §9.3) и MUST читаться сервисами при расчётах (разметка, склейка, глубина ввода). UI изменения настроек и `settings_history` NOT MUST входить в этот пакет (Пакет 3); в пакете настройки изменяются только данными (seed/миграция).

##### Scenario: Настройка влияет на расчёт
- WHEN у пользователя порог склейки отличен от дефолта
- THEN расчёт склейки (FR-13) использует его значение, а не константу в коде

---

### Группа J. Приватность

#### FR-25: Данные только на нашем сервере
Все данные пользователей MUST храниться только на нашем сервере: SQLite-файл и бэкапы локально рядом с ботом (решения 26.10 №6, №7). Передача данных внешним сервисам, сторонней аналитике и любым облачным хранилищам NOT MUST допускаться.

##### Scenario: Проверка хранилища
- WHEN бот работает в штатном режиме
- THEN все записи (users, sleep_events, settings) и их бэкапы находятся на нашем сервере; исходящих передач данных пользователей во внешние системы нет
