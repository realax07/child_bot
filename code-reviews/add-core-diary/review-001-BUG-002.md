## Что проверено

1. **Группа MessageHandler (group=1) и backfill-диалог (WAIT_EVENT_TIME).**
   `src/handlers/__init__.py`: reply-обработчик зарегистрирован в `group=1`,
   backfill `MessageHandler` — в группе 0. PTB диспатчит апдейт в КАЖДУЮ
   группу (первый совпавший в группе), поэтому тексты доходят до обоих.
   Проверено эмпирически (атака A1 ниже): в фазе WAIT_EVENT_TIME оба
   обработчика реально получают апдейт. Обычный ввод времени («14:30»)
   не входит в `state.REPLY_BUTTONS` — `reply_button_message` молчит,
   разбор ведет только backfill (группа 0). Санкционированное отклонение
   (group=1 вместо ограничения filters) корректно задокументировано в
   комментарии регистрации.
2. **Guard «не той» кнопки (design D5).** `reply_event_button`
   (events.py) вызывает `is_stale_callback(conn, …, kind)` →
   `get_state` → `SleepEventsRepo.last` — свежее чтение из БД на каждое
   нажатие, без кэша. Отказ: ALREADY_ASLEEP/STILL_AWAKE + свежее inline-меню,
   записи НЕТ (`_set_pending_kind(None)` попает и WAIT_EVENT_TIME — фазы
   не переживают отказ). Покрыто TC-BUG002-002/004.
3. **«↩️ Отменить последнее» с панели.** `reply_undo_button` (undo.py)
   использует тот же `SleepEventsRepo.delete_last` (ORDER BY created_at
   DESC, id DESC — design D12), те же тексты UNDO_DONE/NOTHING_TO_UNDO,
   что callback `undo:last`; пустая БД — «отменять нечего», данных нет
   (TC-BUG002-007). **Observer-проверка не потеряна**:
   `access.is_observer` (свежее чтение роли, D13) → deny_message без
   удаления — паритет с `undo_last_callback`.
4. **Свежее меню и /start.** После события/отмены с панели —
   `common.send_fresh_menu` по свежему чтению БД (`current_markup`);
   `/start` шлет сообщение-носитель панели (REPLY_PANEL_INTRO +
   ReplyKeyboardMarkup: resize=True, one_time=False — панель не исчезает),
   затем приветствие с inline-меню. Ассерт в test_smoke_core обновлен —
   санкционированное отклонение.
5. **Слои (design D1).** `state.py` — чистые данные без PTB-объектов;
   разметку строит handlers; `get_user` — через сервис. Паритет со
   стилем существующих обработчиков.
6. **SQL/секреты.** Все запросы диффа — через параметризованные
   `?`-плейсхолдеры репозитория (`delete_last`, `last`, `insert`); new SQL
   в диффе отсутствует. Секретов нет (BOT_TOKEN — только env в `--check`).

## Свои атаки (эмпирически, worktree)

- **A1. Панельная кнопка ВО ВРЕМЯ WAIT_EVENT_TIME** (двойной ответ из заметки dev — оценка критичности): подтвержден двойной ответ (§7.12 + §7.10). Фазы после: `pending=sleep`, `wait=None` — консистентно; событий в БД: 0. **Не критично** — UX-шум без порчи данных и без зависшего диалога → замечание #1 (minor). Оценка серьезности S4.
- **A2. Двойной тап «😴 Заснул» при awake (две панели подряд)**: оба нажатия → §7.10, `pending=sleep`, записей 0 — guard по свежему чтению БД не пускает запись до выбора времени; повторный §7.10 безвреден.
- **A3. Undo с панели дважды (вторая — по пустой БД)**: первая — UNDO_DONE + свежее меню; вторая — «Отменять нечего» + свежее меню; событий 0. Данных-мусора нет.
- **A4. Текст кнопки, набранный вручную от неизвестного telegram_id**: обработан как нажатие (создание user — дизайн FR-5, см. note #4); произвольный посторонний текст молчит (TC-BUG002-008).
