# Design (SDD): add-core-diary — ядро дневника сна

- **Флоу:** 1
- **Дата:** 2026-10-26
- **Автор:** СА
- **Трассировка:** requirements.md FR-1…FR-25 (группы A–J); ТЗ §4, §5, §7, §8, §9, §10; решения 26.10 №1–№8

## Решения

| # | Решение | Основание | Альтернатива |
|---|---------|-----------|--------------|
| D1 | Слои: `handlers` (aiogram-free, python-telegram-bot v21) → `services` → `repositories`. Handlers не импортируют репозитории; вся бизнес-логика (разметка, склейка, сводки, конфликты) — чистые функции/классы в services, покрытые юнит-тестами без Telegram и БД | FR-1; ТЗ §8, §10.1 | Монолит-скрипт — отклонено: нет тестируемости расчётов |
| D2 | Фреймворк: python-telegram-bot v21+ (async), `Application.builder()`, long polling на старте; callback-схема из ТЗ §10.3 (`event:sleep`, `event:wake`, `event:sleep:manual`, `event:wake:manual`, `undo:last`, `time:now`, `time:manual`, `conflict:overwrite`, `conflict:cancel`). Отклонение от §10.3 (`event:sleep` = «отметить сейчас», отдельная ветка `backfill:*`) — осознанное, по потоку §4.4/§7.10 | ТЗ §8, §10.3, §4.4, §7.10 | aiogram 3 — отклонено (ТЗ называет PTB) |
| D3 | БД: SQLite, `PRAGMA journal_mode=WAL`, `foreign_keys=ON`; три таблицы `users`, `sleep_events`, `settings` строго по ТЗ §9.1–9.3, плюс колонка `users.role TEXT NOT NULL DEFAULT 'parent'` (решение 26.10 №5). `settings_history` и `daily_summary` НЕ создаются (пакеты 2–3) | FR-2, FR-22; ТЗ §9.1–9.3; решения №5, №7 | PostgreSQL — отклонено решением №7 |
| D4 | Время храним в UTC (`DATETIME`), TZ пользователя (`users.timezone`, IANA-имя) применяется через `zoneinfo` на границе ввода/вывода/разметки. TZ при `/start`: из `language_code` TG-профиля по карте (ru → Europe/Moscow и т.п.), fallback `Europe/Moscow` (аудитория бота) — первое приближение по ТЗ §8.2, подтверждение/смена TZ — вне пакета. Карта кодов — артефакт кода, фиксируется юнит-тестом; для DST-неоднозначного локального времени (ночь перевода часов) парсер принимает ранний вариант (fold=0) | FR-4; ТЗ §8.2; PLAN (риск про TZ) | Хранить локальное время — отклонено: двусмысленность при смене пояса/DST |
| D5 | Состояние ребёнка НЕ хранится отдельно: выводится из последнего события (`wake`/нет событий → бодрствует, `sleep` → спит). Меню строится по состоянию (FR-6). Guard колбэков: устаревшие inline-клавиатуры в истории чата остаются нажимаемыми, поэтому перед созданием события обработчик колбэка перепроверяет состояние по БД; при противоречии нажатие игнорируется (answerCallbackQuery + перерисовка актуальной клавиатуры), противоречивое событие не создаётся | FR-6; ТЗ §4.1, §6 | Таблица состояний — отклонено: рассинхронизация с событиями |
| D6 | Разметка день/ночь, склейка, сводки — чистые функции на лету из сырых `sleep_events` (§9.5). `sleep_type` в момент записи события НЕ вычисляется и НЕ пишется: при «😴 Заснул» → «🕐 Сейчас» конец интервала неизвестен, а правило FR-9/10/11 зависит от конца и длительности; при смене настроек границ ночи (FR-24) сохранённое значение устарело бы без пересчёта. `sleep_type` — результат вычисления при чтении/расчёте; колонка в схеме остаётся (ТЗ §9.2) как nullable-резерв, для логики пакета 1 не используется (при записи NULL, как и `is_merged`). Метка «требует проверки» кладётся в данные события, текст не выводится | FR-3, FR-9…FR-11, FR-13, FR-24; ТЗ §9.5; ОВ-ПО-3 | Писать sleep_type при финализации интервала — отклонено: зависимость записи от настроек и логики разметки, пересчёт при смене FR-24; материализованные агрегаты — отклонено (§9.5 прямо запрещает) |
| D7 | Разметка (чистая функция): ночь, если начало ≥ night_start (19:00) ИЛИ конец ≤ night_end (07:00); иначе день. Начало в [night_start − warn_gap; night_start) (warn_gap = 10 мин, дифференцируемая настройка не требуется в пакете) → дневной + предупреждение «Поздний дневной сон может сдвинуть ночной». Начало в ночном диапазоне и длительность < 40 мин → метка requires_check в данных | FR-9…FR-11; ТЗ §4.2; AC-2 брифа | — |
| D8 | Отнесение сна к дню — единое правило (решение ПМ 26.10): сон относится к странице дня, в которую попадает МОМЕНТ НАЧАЛА сна; страница дня = 06:00 текущего дня → 05:59 следующего (`day_start` из настроек). Для начала в [00:00; 06:00) это страница предыдущего календарного дня (согласовано с «ночь за вчера» — решение продакта №2); ночной сон через полночь вследствие этого целиком попадает в страницу дня начала сна | FR-12; решения №2; решение ПМ 26.10; ТЗ §5 | Отнесение по календарной дате начала — отклонено: для начал в [00:00; 06:00) расходится со страницей дня; делить сон по границе дня — отклонено решением №2 |
| D9 | Склейка (чистая функция): смежные интервалы сна объединяются, если бодрствование между ними < порога `merge_threshold` из `settings` (дефолт 20 мин); порог читается при каждом расчёте — смена порога меняет результат без перезаписи событий. `is_merged` — резерв схемы (ТЗ §9.2), в пакете 1 не пишется ни в каком сценарии (склейка — только вычисление) | FR-13, FR-14; ТЗ §4.3 | — |
| D10 | Ввод задним числом: диалог без БД-FSM — фаза диалога (ожидание времени, тип события) в `context.user_data` PTB (один процесс). Парсер принимает `HH:MM` (сегодня), `вчера HH:MM` (прошлый календарный день 00:00–23:59), `DD.MM HH:MM`; «разрешённое» время в будущем → отказ с предупреждением; старше `backfill_depth_days` (3) → §7.15; нераспознано → §7.12 с повторным запросом | FR-15…FR-17, FR-20; решения №4; ТЗ §4.4, §7.10–7.12, §7.15 | APScheduler/таблица FSM — отклонено: избыточно для пакета (APScheduler — Пакет 2) |
| D11 | Конфликты: пересечение интервала с существующими событиями или нарушение порядка sleep/wake → §7.13 с [Изменить]/[Отменить]. «Изменить» = атомарная перезапись целевого события (UPDATE целевой записи, без дублей) + уведомление (ОВ-ПО-1, рекомендация брифа; статус: рекомендация принята ПМ, применяется по умолчанию — продакт может переопределить). Целевое событие выбирается детерминированно: при нескольких пересечениях — ближайшее конфликтующее по времени; при нарушении порядка — последнее событие, приводящее к нарушению. «Отменить» = no-op. После «Изменить» кнопка «↩️ Отменить последнее» (D12) удаляет перезаписанную запись целиком — прежнее значение НЕ восстанавливается | FR-18; ОВ-ПО-1 | «Спросить какое удалить» — отклонено рекомендацией брифа |
| D12 | «↩️ Отменить последнее»: DELETE последней записи по `created_at`/`id`; состояние и меню пересчитываются (D5). Нет событий → сообщение «отменять нечего», данных нет изменений. Отмена после перезаписи (D11 «Изменить») удаляет перезаписанную запись целиком и не восстанавливает прежнее значение | FR-21; решение №3 | Soft-delete — отклонено: ФЗ не требует истории удалений в пакете 1 |
| D13 | Роль `observer`: проверка роли в обработчиках событийных кнопок — нажатие игнорируется с сообщением о недоступности отметок; просмотр сводок (пакеты 2–3) — без ограничений. UI смены роли — вне пакета. Связь наблюдателя с владельцем данных (linkage observer → родитель) в пакете 1 НЕ создаётся: хранится только `role`; правило «чьи события смотреть» — планируемая additive-миграция в пакете 2/3 | FR-22; решение №5 | — |
| D14 | Настройки: при первом `/start` — seed 13 параметров (12 из ТЗ §5 + «целевая длительность дневного сна» = 90 мин, решение №1) в `settings` по ключам `sleep_min_before_nap` … `day_start` (фиксированный словарь ключей в коде); повторный `/start` — идемпотентен. Сервисы читают настройки через `SettingsService` (кэш на время запроса не допускает устаревания в пакете — читаем каждый расчёт) | FR-5, FR-23, FR-24; решения №1 | Хардкод дефолтов в расчётах — отклонено FR-24 |
| D15 | Приватность: файл БД и бэкапы (`sqlite3 .backup` по расписанию каркаса деплоя) только локально на нашем сервере рядом с ботом; ни один обработчик не отправляет пользовательские данные во внешние HTTP-сервисы; логи — без содержимого сообщений (только user_id и тип события) | FR-25; решения №6, №7 | Облачный бэкап — отклонено решением №6 |

## Затрагиваемое

- Модули/файлы (создаются, зона dev): `src/main.py`, `src/db.py`, `src/handlers/{start,events,backfill,undo,common}.py`, `src/services/{state,event,calculation,settings,access}.py`, `src/repositories/{users,sleep_events,settings}.py`, `tests/**`.
- Миграции: первичная схема (D3); обратимость на этапе каркаса не требуется (БД с нуля), дальнейшие — additive.
- Сквозные процессы: планировщик APScheduler — НЕ подключается (Пакет 2); тексты §7 фиксированы в отдельном модуле `src/texts.py` для дословного соответствия AC-6 брифа.

## Допущения

- TZ из TG-профиля недоступен напрямую (Bot API не передаёт) — используется карта `language_code` → IANA, fallback Europe/Moscow; подтверждение TZ у пользователя — вне пакета (не проверено на проде, см. PLAN «Риски»).
- Порог предупреждения «поздний дневной сон» = 10 мин до ночной границы (в требованиях «например, 18:50») — константа кода, не настройка (не проверено, правится одной строкой).
- «Вчера» вычисляется от локальной даты пользователя в момент ввода (проверено юнит-тестами на сценариях FR-20).
