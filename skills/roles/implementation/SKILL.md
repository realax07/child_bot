# Реализация задачи по спеке

Как реализовать одну задачу tasks.md так, чтобы код прошел ревью с первого раза: поведение из сценария, API из SDD, коммит с трассировкой.

## Когда применять

- Оркестратор назначил задачу dev-агенту (одна задача = одна сессия)
- Исправление замечаний ревью по задаче

Не применять для: изменения спеки (эскалация через СА), тест-кейсов и автотестов QA (другие роли).

## Процедура

1. **Прочитай задачу и её след.** Номер задачи → строка в tasks.md → какие Requirement/Scenario домена она реализует. Составь себе список проверок: каждый Scenario задачи — будущий пункт локальной проверки.
2. **Прочитай контракты.** API-пути, схемы, коды ошибок — из sdd.md; техрешения (сессии, fast line ≤1, поиск) — из design.md. Сверяйся с ними ДО написания, а не после: расхождение API — blocker на ревью.
3. **Проверь зависимости.** Если задача опирается на каркас/предыдущие задачи — убедись, что они в репозитории (сборка/запуск). Сломанная зависимость — эскалация, не героический ремонт чужого.
4. **Пиши минимально и по спеке.** Один сценарий — одна очевидная реализация. Соблазн «заодно доделать» соседнюю задачу откладывай в отчет оркестратору: вне-trассировочный код — blocker ревью.
4a. **Ничего выдуманного (J45, zero-hallucination):** API/функция/переменная используются только после подтверждения их существования в кодовой базе (grep/чтение); сигнатуры и поведение — из кода, не из памяти модели. Не уверен, что модуль существует — проверь до импорта. Паттерн «наверное там есть хелпер» — сначала grep.
4b. **Минимализм (J45, minimalist):** новая зависимость/слой/абстракция — только если без неё задача не решается (ОГР-1); «пригодится потом» — не основание. Самое простое работающее решение, соответствующее спеке, — правильное.
5. **Негативные ветки — сразу.** 400/401/409/422 пути реализуй в той же задаче, что и позитивные: ревью проверяет ВСЕ сценарии задачи, недоделанный негатив вернет задачу целиком.
6. **Окружение отдельно от кода.** Пароли, пути к БД, порт — переменные окружения; файл БД — вне репозитория (NFR-5). В git не должно попасть ничего из этого.
7. **Локальная верификация.** Подними приложение, пройди каждый Scenario руками (включая негативные) или коротким скриптом-смоуком. Несовпадение факта со сценарием: если спека непротиворечива — исправь код; если спека противоречива/нереализуема — стоп-эскалация с repro.
8. **Коммит и чекбокс.** Один логический коммит с номером задачи в сообщении («task 2.3: …»); чекбокс задачи в tasks.md отметь; прогони `openspec validate --all --strict` и `flow_check.py`.
9. **Отчет оркестратору:** что сделано, какие сценарии проверены (списком), какие вопросы остались. Отчет — основа ревью: неполный отчет удлиняет ревью.

## При исправлении замечаний ревью

Чини только отмеченное; параллельные «улучшения» создают новый диф и новый круг ревью. Не понимаешь замечание — вопрос оркестратору, а не спорная правка.

## Ошибки

- Реализация «по памяти» без перечитывания сценариев — упущенный негативный путь вернется ревью.
- Вызов несуществующего API/хелпера «по памяти модели» — ноль работы до первого запуска (zero-hallucination).
- Over-engineering: слой/интерфейс/конфигурация «на будущее» — не трассируется на Scenario, blocker ревью (minimalist).
- Хардкод окружения (порт, путь БД, пароль) — мгновенный major.
- Догадка в трактовке двусмысленного сценария вместо эскалации — самая дорогая ошибка: исправление после вливания дороже вопроса до.
- Чужие задачи трогать («там же одна строка») — ломает изоляцию задач и ревью.
