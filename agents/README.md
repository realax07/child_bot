# Агенты конвейера — реестр, вход/выход, назначение

> Каждый файл в этой папке — **системный промпт** сабагента: подается целиком как системное сообщение при запуске на задаче. Здесь: кто эти агенты, что делают, зачем нужны, что принимают и отдают. Общий процесс — [../README.md](../README.md), оперативные правила — [../AGENTS.md](../AGENTS.md).

## Почему агентов именно столько

Одна роль = один изолированный контекст = одна ответственность. Автор не ревьюит себя; ревьюер не пишет код; аналитик требований не решает архитектуру. Изоляция дает три вещи: независимую валидацию (глаза без конфликта интересов), короткий чистый контекст (агент не тащит чужие детали), подменяемость (промпт + задача = любой запуск воспроизводим).

## Режимы запуска

- **plan** — только анализ и диалог, запись в репозиторий запрещена.
- **plan-write** — диалог + запись артефактов своей роли (без push). Для БА: черновик → подтверждение Заказчика → запись.
- **auto-edit** — запись в своей зоне разрешена; push main и чужие зоны запрещены (стандарт конвейера).
- **yolo** — полный доступ; в конвейере не используется (только песочницы).

## Агенты: назначение, вход/выход, зачем нужен

### 1. Бизнес-аналитик — [ba_agent.md](ba_agent.md)

**Зачем:** переводит слова Заказчика в проверяемые требования, не добавляя отсебятину. Единственный, кто говорит с Заказчиком (через ПМ) на этапе анализа. Лимит: максимум 2 раунда открытых вопросов, далее — дефолты «примем X, возразите».

- **Вход:** запрос Заказчика (тема, ответы ОВ-N дословно).
- **Выход:** `requirements.md` (7 разделов, FR-N/NFR-N, MoSCoW, преамбула статуса/автора/истории) + `docs/ba/answers_roundN.md` (дословные цитаты, связь ОВ-N → изменение) + `docs/product-overview.md` (мастер-док, обновление на каждом change).
- **Ключевые границы:** не проектирует архитектуру; не закрывает открытые вопросы сам; противоречия фиксирует, не разрешает.
- **Передает:** СА (только при статусе УТВЕРЖДЕН — решает Заказчик).

### 2. Системный аналитик — [sa_agent.md](sa_agent.md)

**Зачем:** превращает требования в формальный контракт поведения (спека OpenSpec) и план реализации (tasks.md). Здесь требования становятся тестируемыми: каждый Requirement получает Scenario GIVEN/WHEN/THEN.

- **Вход:** УТВЕРЖДЕННЫЙ `requirements.md` (+ answers-артефакты всех раундов).
- **Выход:** `openspec/changes/<id>/` (proposal, дельты specs, design, tasks) + `sdd.md` (стек, API-контракты, модель данных — служебные эндпоинты обязательны).
- **Ключевые границы:** спека описывает наблюдаемое поведение, не реализацию; не начинает без УТВЕРЖДЕНО и без плана пакета (J41 — PLAN-файл пишет ПМ); не трогает чужие change-пакеты.
- **Скиллы:** `openspec-authoring`, `service-decomposition` (границы сервисов, владение схемой, сквозные процессы, швы делегаций — при нарезке пакета), `requirements-elaboration` (трактовка ТЗ), `factory-flow`.
- **Передает:** dev (задачи), qa_case_author (спека как прямой источник кейсов — remove-qa-checklist). После реализации — архивация дельт в master-spec (контракт 7).

### 3. Разработчик — [dev_agent.md](dev_agent.md)

**Зачем:** реализует ровно одну задачу tasks.md в изолированной сессии — узкий контекст = глубокая концентрация + дешевый откат.

- **Вход:** задача из tasks.md (текст + ссылки на спеку/дизайн), ветка `feature/<change-id>-<NN>` от main.
- **Выход:** код в ветке + PR (gh) + чекбокс задачи. Ревьюеру — процедура проверки в ТЗ.
- **Ключевые границы:** спека — арбитр (расхождение = эскалация, не правка); не реализует вне tasks.md; не пишет QA-артефакты; push main запрещен.
- **Принимает:** вердикт code_reviewer (approve → merge ПМ; return → доработка в той же ветке).
- **Смежная зона:** изменения пайплайна (flow_check, flow.yml, scripts/) — тоже его зона (G7: DevOps-агента нет).

### 4. Код-ревьюер — [code_reviewer_agent.md](code_reviewer_agent.md)

**Зачем:** независимая валидация кода: три круга (спека как закон → best practices → интеграция) + регресс-прогон вместо своих смоков. Главный фильтр качества: ловит то, что автор не видит (гонка 5.1, дыры fast line — найдены именно здесь).

- **Вход:** PR диффа + спека задачи + процедура проверки из ТЗ.
- **Выход:** вердикт approve/return + таблица замечаний (blocker/major/minor + рекомендации) в `code-reviews/`.
- **Ключевые границы:** не правит код сам; «я бы написал иначе» — не замечание; documentation в диффе проверяется буквальным воспроизведением.
- **Действие:** `code_review` (Флоу 1/4); с решением 2026-10-07-code-review-flow2 — также во Флоу 2 (bug_fix → code_review → accept_review → merge_task).

### 5. QA: автор тест-кейсов — [qa_case_author_agent.md](qa_case_author_agent.md)

**Зачем:** развертывает каждый Scenario спеки в исполняемый кейс: предусловия, атомарные шаги, проверяемое ожидание (код + тело/состояние), конкретные данные. Этап чеклистов упразднен (remove-qa-checklist): кейсы пишутся по спеке (Requirements + Scenarios) напрямую, трассировка — TC → Requirement/Scenario. Здесь рождается точность, по которой потом пишутся тесты и судятся падения.

- **Вход:** спека change-пакета (дельты или master-specs) + `sdd.md` как арбитр структур.
- **Выход:** `test-model/new/<id>/` — TC-N (1 кейс = 1 Scenario; формат «1 кейс = 1 файл» — H1, при внедрении); каждый кейс с источником `Requirement:`/`Scenario:` из спеки.
- **Ключевые границы:** не меняет спеку; дефекты спеки — эскалация, не правка; не объединяет/дробит сценарии; негатив/границы обязательны для требований с валидацией.

### 6. QA: ревьюер тест-кейсов — [qa_case_reviewer_agent.md](qa_case_reviewer_agent.md)

**Зачем:** независимая проверка кейсов (оси: трассировка к спеке, покрытие сценариев, негатив/границы, дефекты спеки, воспроизводимость, данные) + ревью кода автотестов (G8: ассерты дословны кейсу, изоляция, детерминированность, селекторы, TC-ID). Только он переносит кейсы в approved/ — единственный источник законных автотестов.

- **Вход:** кейсы в `new/` + спека (Requirements + Scenarios — арбитр покрытия; + код тестов на G8-итерации).
- **Выход:** `test-model/reviews/<id>/review-NNN.md` (append-only итерации) + вердикт; при approve — перенос в `test-model/approved/<id>/`. Дефекты спеки — фиксируются в review (append-only) и эскалируются.
- **Ключевые границы:** не правит кейсы сам; не одобряет с blocker/major; спор = спека, не мнение.

### 7. QA: автоматизатор — [qa_automation_agent.md](qa_automation_agent.md)

**Зачем:** превращает approved-кейсы в постоянный регрессионный набор — то, что гоняется перед каждым релизом и защищает от регрессий навсегда. Падение теста на корректном коде = баг-репорт, а не правка теста.

- **Вход:** только approved-кейсы (контракт 6).
- **Выход:** `tests/api/` (pytest+requests), `tests/web/` (Playwright) — селекторы дословно из кейсов, автожидания, sleep=0, TC-ID в docstring, метка `# regression: keep|candidate-archive` (G5); баг-репорты в `test-model/bugs/BUG-NNN`.
- **Ключевые границы:** не трогает код продукта; не подгоняет тест под сломанное поведение.

### 8. QA: impact-аналитик — [qa_impact_analyst_agent.md](qa_impact_analyst_agent.md) (создан по H5, в бою с Р4; с 2026-10-10 — J32-легкий: «Зоны воздействия», «Сквозные процессы», сверка плана прогонов)

**Зачем:** держит регресс актуальным при изменении поведения. Когда СА готовит MODIFIED/REMOVED дельты, часть существующих тестов устаревает: они тестируют старое поведение. Impact-аналитик до написания кейсов сверяет дельты с существующим набором и выносит вердикт по каждому затронутому тесту — иначе устаревший тест стреляет ложным пожаром на релизном прогоне.

- **Вход:** дельты change-пакета (MODIFIED/REMOVED Requirements) + манифест регресса + трассировка TC ↔ Requirement.
- **Выход:** `test-model/impact/<change-id>.md` — вердикт по каждому затронутому тесту: **keep** (не затронут) / **revalidate** (поведение изменилось → тест помечается `pending_update`, исключается из релизного прогона, кейс обновляется в `new/`) / **retire** (тестировал удаленное → переносится в архив). Плюс (J32-легкий, 2026-10-10): разделы «Зоны воздействия» (сервисы/модули/контракты), «Сквозные процессы» (деплой/бэкап/смоук/миграции), «План прогонов» (сверка плана SA с вердиктами).
- **Ключевые границы:** не правит тесты сам (только вердикты); семантику «действительно ли изменилось поведение» сверяет со спекой, не с кодом.
- **Передает:** qa_case_author (требования «обновить кейс X» — прямые изменения кейсов в `new/`, remove-qa-checklist), qa_automation (pending_update-метки).

### 9. QA: регресс-аналитик — (промпт создается при первом пост-релизном пересмотре набора, G5; до того метки regression: keep|candidate-archive в тестах пишет qa_automation)

**Зачем:** пост-релизно решает судьбу каждого теста: keep (устойчивое поведение — гоняется всегда) или archive (разовое — миграция, тест конкретного бага). Держит регресс компактным и быстрым на дистанции.

- **Вход:** метки `regression: keep|candidate-archive` + обоснования из тестов + спека.
- **Выход:** `test-model/regression/manifest.md` — тест → решение + причина.
- **Ключевые границы:** работает по меткам и оглавлению, не по всему коду; архивируемые тесты переносятся в `tests/archive/` (не удаляются).

### 15. Основная сессия = relay

Основная сессия — диалог с Заказчиком; конвейерная работа — в сабагентах. **ПМ-сабагент (J1–J3) не внедряется** (решение Заказчика 2026-10-10: сабсабагенты — лишний уровень; параллельные проекты = второй Hermes на другой VPS; новый проект = новая директория + сброс сессии). Дизайн сохранен: [pm_agent.md](pm_agent.md), bounds-проверки `scripts/pm_bounds_check.py` действуют на main-сессию.
