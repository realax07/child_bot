# AI Factory — конвейер агентов

> Ссылки: делегации/возвраты/пинги/Codex/мертвые сессии — `references/subagent-delegation.md`; волновые ревью/отладка/релизный порядок (J10, J25 дизайн-макет, J23 замеры, J26) — `references/wave-review-and-debug.md`; сводка циклов wiki — `references/wiki-progress.md`; эшелоны регресса, freeze tooling, static_v-бамп до devops, гигиена веток ПМ, контракты в промптах ролей — `references/regress-and-deploy.md` (грузить перед regress-final/деплоем и при «долго/много ошибок»). Состояние проектов — только из PLAN.md/BACKLOG.md репозиториев.

Работа в долгом проекте пользователя «Конвейер агентов»: конвейер разработки ПО из агентов-сабагентов. Роль главной сессии — ассистент Заказчика: вести план, наполнять репозиторий артефактами, запускать роли по цепочке.

**Терминология (требование Заказчика):** главная сессия — «ассистент»; Заказчик общается только с ней. «ПМ» — имя роли САБАГЕНТА (`agents/pm_agent.md`), не название этой сессии: в докладах Заказчику, планах и артефактах главную сессию называть «ассистент», а «ПМ» употреблять только про делегированную роль. Правило «ПМ не исполнитель в продуктовом репо» действует для главной сессии в полном объеме — просто под правильным именем.

0. `AGENTS.md` в корне репозитория — входной файл, harness грузит его сам: порядок чтения, flow, rules, паттерн оркестрации.
1. `openspec/specs/{pipeline,artifacts,qa-pipeline}` — правила конвейера. Проверка после любого изменения: `openspec validate --all --strict`. CLI живет в npm-глобале поверх инструментов Hermes — после обновления Hermes/нод-тулз он пропадает вместе с каталогом: проверять `openspec --version` перед воротами и ставить заново `npm install -g @fission-ai/openspec@1.13.0` (одна команда, минуты).
2. `contracts/artifact_contract.md` — контракты 1–7: условия входа/выхода артефактов между ролями; контракт 7 — архивация change в master-spec.
3. `agents/*.md` — системные промпты ролей. Единая анатомия: Роль → Режим запуска → Скиллы (таблица «какой и когда грузить») → Вход → Выход → Границы → Эскалация. Реестр — `agents/README.md`.
4. `skills/*/SKILL.md` — процедуры по гайду Anthropic: description = триггер загрузки, imperative form, объяснять «почему», раздел «Ошибки» с механизмами, а не запретами.

Изменение процесса: сначала спека OpenSpec, затем контракт, затем промпты. После каждого шага обновлять `PLAN.md` и `README.md` репозитория и коммитить — пользователь просил держать документацию актуальной.

## Режимы запуска агентов

- **plan** — анализ и черновики, запись в целевой репозиторий запрещена (чисто диалоговые роли).
- **plan-write** — диалоговая роль с записью артефактов своей роли в целевой репозиторий (без push); промежуточные итерации в диалоге, в репозиторий — только согласованные версии. Стандарт для БА: черновик → подтверждение Заказчика → запись `requirements.md` + `docs/ba/answers_roundN.md`. Таблица зон записи всех ролей — норма в `agents/README.md`; запись вне зоны = нарушение флоу.
- **auto-edit** — стандарт для фабричных агентов: запись артефактов своей зоны свободно; push и выход за зону — только через ПМ.
- **yolo** — полный доступ; в конвейере не используется.

Push-политика (AGENTS.md правило 4): сабагент коммитит локально, пушит только оркестратор после валидации отчета; прямые push в main запрещены. Исключение G6: dev пушит СВОЮ ветку `feature/<change-id>-<NN>` для создания PR — merge в main только оркестратором после approve ревьюера; return = доработка в той же ветке. Мелкие задачи (single-file, <50 строк) — прямой коммит в main по решению ПМ.

## Поток конвейера

`requirements.md` (БА + Заказчик) → OpenSpec-пакет + `sdd.md` (СА) → Разработка (цикл на задачу: один dev-сабагент в изолированной сессии → отдельный сабагент-код-ревьюер → approve/return, return = доработка и повторное ревью; параллелить только задачи с непересекающимися путями записи) → QA-контур: `test-model/checklists/` → `new/` ⇄ ревью (цикл до «одобрить») → `approved/` → автотесты (pytest + requests/playwright). Автотесты пишутся только по approved-кейсам; красный тест на верном коде = баг-репорт. После реализации change архивируется (контракт 7): дельты сливаются в `openspec/specs/` — это master-spec «as is», пакет уходит в `changes/archive/<дата>-<id>/`. Триггер архивации: все tasks `[x]` + зеленый QA + разрешение ПМ. Правка master-spec напрямую мимо change запрещена — теряется аудит «почему изменилось».

## Детерминизм флоу: исполняемые ворота

Порядок артефактов гарантируют не правила, а `scripts/flow_check.py <repo>` (state machine по файлам, exit 1 при нарушении) + CI `.github/workflows/flow.yml` (openspec strict + flow_check на каждый push — нарушение невозможно смержить). Перед приемкой этапа гоняй flow_check; при старте QA в проектном репозитории скопируй туда flow_check и workflow. Ворота проверяют порядок и трассировку, не смысловое качество — качество остается за ревью-циклом. Поверх flow_check работают план релиза (J41), энфорсер делегаций (J43) и память фазы — механика в `references/flow-enforcement.md`.

- **Архивация change (контракт 7) — механика и два решения ПМ:** слияние дельт делегировать СА (он же делал пакет — знает структуру; занимает минуты): ADDED-домены создаются как spec (убрать заголовок Delta, оставить Purpose/Requirements), MODIFIED — замена Requirement целиком (не задвоить — проверка: grep старой формулировки в master-spec), пакет целиком через git mv в changes/archive/<дата>-<id>/ (история сохраняется), в активных changes/ остается только archive/. Ожидание по validate: число спек = было + новые домены. ДВА РЕШЕНИЯ ПМ при архивации: (1) корневой sdd.md — если дельты меняли API/модель данных, контракт предписывает обновить; при отсутствии СА-задачи приемлемое решение — sdd пакета в archive считается документированной дельтой, синхронизация корневого sdd — S-задача СА перед следующим пакетом (BACKLOG E8); (2) перенос sdd в архив НЕ снимает обязательств по его эскалациям — переносить их в PLAN/бэклог. G8-ревью кода тестов (оси: ассерты дословны кейсу, изоляция, детерминизм sleep=0, семантические селекторы, TC-ID, метки G5) гонять как ОТДЕЛЬНУЮ сессию от ревью кейсов — по одной на обе тестовые ветки сразу; вердикты по каждой ветке отдельно. find major (ослабленный ассерт, маскирующий расхождение с sdd) = возврат: тест → xfail(strict) + баг-репорт на расхождение (прецедент BUG-003), не приемка с замечанием — ослабленный ассерт в регресс-наборе молча пропускает расхождение навсегда.

## Оркестрация: роли как контекстные окна

Роли запускать только сабагентами через `delegate_task` — контекст изолирован (проверено живым тестом): сабагент не видит диалог и память ПМ, получает лишь goal/context. В goal передавать: системный промпт роли из `agents/*.md` целиком + задачу с путями входных артефактов + зону записи; ответы Заказчика — дословно. Выполнять роль в основной сессии ПМ запрещено (контаминация контекстов ролей). Отчет сабагента принимается после валидации артефактов в репозитории и зеленого flow_check — сам отчет не является доказательством. Ревьюер обязан верифицировать заявления dev фактически (поднять приложение, прогнать миграцию, прострелить эндпоинты), а не поверить отчету; фиктивные проверяемые утверждения отлавливаются именно так.

**Порядок этапа разработки: dev → code_reviewer → merge (dev-lead), и никак иначе — пропуск ревью = то же нарушение, что ручной merge ПМ:** в goal dev-сабагентам merge не предусмотрен и запрещен; ветки после dev ждут ревью. Роль code_reviewer существует в реестре, но её неиспользование не ловится дисциплиной — правило «отдельный ревьюер на каждую задачу» (AGENTS.md) без исполняемых ворот соблюдается только пока ПМ не устал/не забыл (прецедент: 7 dev-веток слиты без единого вердикта). Хардкод (J10, четыре уровня): flow_check — закрытые dev-задачи в tasks.md без approve-вердикта в code-reviews/<change-id>/ = FLOW-ERROR; pr_validate/flow.yml — PR без review-файла = FAIL; pm_bounds_check --require-review — merge без вердикта датой раньше = FAIL; dev_lead — нет approve по ветке = стоп. Если ворота ещё не внедрены, а ревью пропущено — ревью задним числом ОБЯЗАТЕЛЬНО до дальнейшего продвижения, это не «прощение» этапа. Внедряя ворота на артефакт-имена, сверяй формат имени в регэкспе ворот с форматом, выданным в ТЗ ревьюеру, ДО спавна: расхождение (`review-<NNN>-<задача>.md` против `review-<задача>-<NNN>.md`) делает approve-файлы невидимыми для ворот — красный негатив выглядит как «ревью еще нет», и ворота чинят не там. Новый формат имени = правка регэкспа в той же сессии + прогон ворот на реальных файлах. Один review-файл может покрывать несколько задач (имя вида review-NNN-2.1-2.2-slug.md при задачах, сделанных одним dev-коммитом) — ворота обязаны извлекать ВСЕ числовые task-ID из имени файла, а не первый: парсинг только ведущего ID дает ложный красный «2.2 без ревью» при фактическом approve. Авторство вердикта механически пока не проверяется (J11, бэклог): ПМ мог бы нарисовать approve сам и ворота позеленели бы — не делать этого ни при каком давлении сроков, вердикты пишет только делегированный code_reviewer; диагностика/регресс на итоговом дереве — тоже делегированная работа, не ПМ. Ролевая территория не ограничивается код-ревью: ПМ, который сам делает диагностику/регресс/фиксы в продуктовом репо (даже «это же быстрее»), повторяет то же нарушение — Заказчик формулирует это как «ты сам что ли делаешь? а как же dev-сабагенты?». Диагностика падения сьюта, merge-конфликт, отладка стенда — делегированные работы; ПМ верифицирует результат прогонами ворот, но руками продукт не трогает.

**Механика dev-lead при консолидации (первый полный прогон роли — факты):** вердикт-гейт J10 — «обе стороны закрыты»: ветка БЕЗ ревью (bugfix между релизами) закрывается самостоятельным независимым ревью дифа dev-lead-ом, review-файл коммитится в main ДО merge ветки (иначе ворота после merge красятся). Формат вердикта — однострочный `## Вердикт: approve` (многострочный `## Вердикт` + жирное тело тоже парсится регэкспом `#{1,4}\s*Вердикт\s*:?(.+)`, но однострочный надежнее). Review-файл покрывает task-ID, извлеченные из ИМЕНИ файла (`review-002-bug003-fix.md` → «003») — имя выбирать так, чтобы извлеченный ID не совпал с номером реально закрытой задачи, иначе ворота требуют approve и для нее (задача 5.2 с именем-суффиксом `-5.2-…` как раз парсится безопасно: 5.2 не в closed). Регресс — единый стенд по tests/README после всех мерджей: свободный порт (socket bind :0), `env -u EKOTOV_WIKI_BASE_URL -u EKOTOV_WIKI_DB_PATH`, схема `python -m app.db` + seed owner/wife через piped stdin в `app.seed_users` ДО pytest, иначе 500 на login и лес ERROR на фикстурах.

**Merge и консолидация результатов dev — роль dev-lead, не ПМ (J9):** merge-план, слияние, конфликты, финальный регресс — сабагенту по `agents/dev_lead_agent.md`; триггер — БОЛЬШЕ одной параллельной dev-сессии (реальная консолидация: merge-план нескольких веток, кросс-конфликты, сводный регресс); при одиночной dev-ветке merge выполняет ПМ в обычном цикле после approve ревьюера — уточнение Заказчика, dev-lead на одну ветку не вызывается. Гарантия неисполнительства ПМ — механическая, не дисциплинарная: `pm_bounds_check.py --product-commits RANGE --repo <repo>` (коммит ПМ-сессии в продуктовом репо без пометки `[pipeline]` = FAIL по git-истории; exit-код ворот проверять изолированным вызовом без пайпа — `cmd | tail; echo $?` возвращает exit tail, не скрипта; ворота верифицировать негативом на реальном прецеденте, не только /tmp-фикстурах). Резолюция конфликтов при слиянии параллельных веток: спека главнее кода, более новый флоу главнее старого (замена пресета поверх базы), семантический конфликт — стоп-эскалация архитектору; после серии мерджей дедупить tasks.md — параллельные ветки отмечают чекбоксы независимо, задвоенные ID задач ловит `openspec validate --strict`. Заказчик читает участие ПМ в продуктовом коде как жжение контекста дорогой модели — ручные merge/отладки ПМ в продуктовом репо недопустимы даже когда «быстрее сделать самому».

## Эскалации спеки

Dev/ревьюер не правят спеку под код — эскалируют ПМ. Обработка ПМ: признать дефектом спеки → задача СА с приоритетом «до задачи X» (указать конкретную зависимую задачу); параллельные задачи без пересечения зоны MAY идти, пока СА правит. Minor-находки ревью, относящиеся к спеке (неспецифицированный контракт, уточнение формулировки), накапливай списком в PLAN.md и передавай СА одним пакетом при ближайшем его запуске — поштучный запуск СА ради одной строки дороже пакета. Прецедент: health-эндпоинт против «401 на все /api/*» — фиксируется exempt-список в sdd + MODIFIED-дельта auth.

Структура `docs/product-overview.md` проектного репо (владелец БА, обновление — обязательный артефакт контракта 1 на этапе БА каждого change: обновить или явно подтвердить актуальность): Суть и пользователи → Домены (ссылки на master-specs, as-is формулировки, решения инкорпорированы в описание без хронологии) → Ключевые договоренности (устойчивые решения по блокам) → Глоссарий → Ограничения среды. БА-обновление: вносить только изменения, затронутые change; остальное — подтверждение актуальности в отчете.

## Флоу задач: 5 типов (выбор — обязанность ПМ, слепая зона была)

Стоящее правило плана задачи: **каждая задача начинается с плана в .md** (в PLAN.md проекта или отдельном файле задачи) — состав изменений, порядок работ, артефакты, и сразу **декларация флоу** (1–5) — Заказчик видит выбор до запуска. Формулировка без указания флоу = план не готов, задача не стартует.

1. **Флоу 1 — новый функционал**: полный цикл (БА → СА → change-пакет → задачи → QA → релиз). Любое новое поведение, изменение поведения, новые сущности.
2. **Флоу 2 — баг-фикс, без БА и СА**: баг = расхождение реализованного с существующей спекой — формулировать требования и проектировать нечего. BUG-NNN в test-model/bugs/ → ПМ валидирует → dev в feature/bug-NNN → PR → code_reviewer → merge. Граница «баг vs фича»: фикс легален без СА только если ожидание ВЫВОДИМО из существующих Requirements; если меняет поведение, которого спека не описывает, или трогает схему/API-контракты — мини-дельта СА обязательна даже для бага. ПМ проверяет выводимость при валидации баг-репорта (на BUG-001 граница была пройдена интуицией — правило теперь писано).
3. **Флоу 3 — hotfix на проде**: откат деплоя → немедленное уведомление Заказчика → фикс по Флоу 2 параллельно. Только недоступность/потеря данных; контур описан, не обкатан.
4. **Флоу 4 — обслуживание** (чистка, линтеры, рефакторинг, зависимости): мини-ТЗ прямо в делегации, без БА; меняет спеку → СА мини-дельта; иначе сразу dev/qa_automation + стандартный PR-цикл.

5. **Флоу 5 — экспресс-режим (Флоу 1 без БА/СА, ретроспективная документация):** легален ТОЛЬКО при всех трех условиях — S-объем, одна зона, поведение очевидно Заказчику (он словесно подтвердил именно это решение). Dev-цикл запускается сразу, но в ТОМ ЖЕ цикле документация догоняет код цепочкой ролей: БА (requirements по дословным словам Заказчика) → СА (дельта спеки) → impact → чеклист → кейсы → ревью → тесты. Арбитр ретроспективы — фактически реализованный код (сверять каждый пункт с ним), а не формулировка ПМ: ПМ-контекст галлюцинирует детали (прецедент: «tags в JSON tasks.tags» против реальной нормализованной схемы tags+task_tags — dev поймал и исправил сам). Применение Флоу 5 без ретроспективы = «сразу код», деградирует в неуправляемый процесс (прецедент R1.3: P4 запущен сразу в dev). Метка флоу обязательна: в goal делегации «Флоу: N» + обоснование одной строкой, и в журнале делегаций PLAN.md — иначе выбор флоу неаудируем.

Все 5 флоу и сводная таблица выбора — в корневом README.md фабрики. Держать синхронизированным: новый тип работ = новый флоу или явное расширение таблицы, не импровизация.

## Здоровье сабагентов (пинг на деградацию)

Сабагенты деградируют: модель уходит в токен-делириум (петли фраз «connectivity pending», мусорные символы) и жжет бюджет без результата — реальный случай 37 минут вхолостую. Контроль ПМ:

- **Пинг каждые 5–10 минут активной сессии:** `tail -c 800 ~/.hermes/cache/delegation/live/deleg_*/task-0.log` (последние tool-вызовы). Здоровье = осмысленные вызовы и прогресс по файлам; деградация = повторяющиеся фразы, невнятные символы, отсутствие tool-вызовов. Закончил — приемка, реестр почистен.
- **При деградации — немедленный stop** (delegate_task action=stop), перезапуск с чистого листа КОМПАКТНОЙ формулировкой задачи (деградировала первая попытка с длинным брифом; перезапуск с «12–18 пунктов, без прозы» закрыл задачу за 3.5 мин); артефакты деградировавшей сессии не использовать даже частично осмысленные, репо после нее проверять на мусор.
- **Живое управление через action=steer** — директива дописывается к следующему tool-результату сабагента: ускорить финал («время вышло, вердикт из проверенного»), отменить свою же предыдущую директиву (Заказчик сказал «пусть продолжает»), подправить курс. Директиву можно отменить новой — сабагент выполняет последнюю.
- ПМ не ждет пассивно: между пингами — валидация готовых артефактов и подготовка следующего шага цепочки.
- **Сабагент уперся в лимит итераций (TRUNCATED, ~250 вызовов) — хвост доделывает ПМ, не перезапуск:** работа почти закончена (файлы созданы, прогон выполнен), но без коммита или контрольного прогона. Порядок: прочитать раздел «Незакрытое» отчета → выполнить контрольные прогоны самому → закоммитить самому → реестр почистить. Это лимит, не деградация — переигрывать с нуля дорого и бессмысленно.

## Роутинг-инциденты: Заказчик «провалился в сабагента», длительное молчание

Диагностика — по логам, не по догадкам: grep `~/.hermes/logs/gateway.log` по `inbound message|response ready|routing|Pinned|stale` в таймстамп-окне инцидента восстанавливает, какая сессия отвечала на каждое сообщение; `agent.log` (`model=`, `failover`) показывает молчаливую смену модели при ошибке провайдера — источник «завис на полчаса» без единого сообщения в чат.

- **Типовой механизм захвата чата:** async-доставка завершения делегации/ее background-процесса пинит ключ роутинга домашнего чата на owning-сессию; если та уже ended (после /stop, session_reset, исчерпания), ключ висит на ended-сессии, и на сообщения Заказчика отвечает зомби-артефакт чужой сессии (включая потоки чужих отчетов). Строка `dropping stale entry and recovering/recreating the session` в логе = момент самолечения; heal срабатывает только на ВХОДЯЩЕМ сообщении, не на доставке — до следующего сообщения Заказчика канал может отдавать чужое. Переключение сессии делает сам Заказчик (/new или смена в UI) — ПМ не «перехватывает» канал сам.
- **Действия при таком инциденте:** показать Заказчику механизм и момент самолечения строками лога; зафиксировать инцидент в BACKLOG фабрики; меры к уровню Hermes формулировать как требования к апстриму («исходящие в home channel — только от главной сессии», heal при доставке, а не только при inbound).
- **Залипший ключ роутинга лечится механически, а не только требованиями к апстриму — cron-вотчдог `scripts/session_watchdog.py`** (в фабрике и в `~/.hermes/scripts/`): `hermes cron create '*/2 * * * *' --name session-watchdog --no-agent --script session_watchdog.py --deliver local`. Скрипт читает state.db: ключ `gateway_routing` вида `agent:main:telegram:dm:*` указывает на сессию с непустым `sessions.ended_at` → запись удаляется (плюс ghost-записи `sessions.json`, ссылающиеся на отсутствующие в state.db сессии); следующий inbound создает свежую сессию главной — Заказчик больше не проваливается в зомби. Порядок внедрения: dry-run на живой базе → негатив на фикстуре (временный HOME с копией скрипта и собранным руками state.db: ended-строка, живая строка, ghost-запись) → контроль живого тика по `~/.hermes/cron/output/<job-id>/`. Питфоллы: `sqlite3.connect('file:...?mode=rw')` без `uri=True` дает «unable to open database file»; exit 1 — только при реальном лечении (сигнал для failure-deliver), dry-run всегда 0; живые ключи и живые записи sessions.json не трогать. Уровень Hermes остается требованием к апстриму: вотчдог закрывает симптом в течение интервала крона, не причину; фактическую версию сверять `hermes --version` — свежий апстрим мог починить корень, тогда вотчдог снимают.
- **Подозрение пало на свой скрипт — проверь его подключение, прежде чем соглашаться:** пассивные пост-фактум валидаторы (типа pm_bounds_check) физически не могут перехватывать чаты/сессии; перед разбором проверь, установлен ли вообще подозреваемый слой (git hooks, core.hooksPath, вызовы из конфигов/CI). Это снимает ложную версию за минуты и дает Заказчику проверяемый факт вместо оправдания.

Роль без промпта в agents/ + строки в таблице зон + записи в реестре — не роль, а импровизация. Дизайн-роль — артефакты (мокапы/токены) в design/ проекта как спецификация для dev, не прод-код; выбор из 2–3 контрастных вариантов (эволюция текущего / контрастный / альтернативный язык) — Заказчику, с фиксированным обязательным минимумом по спеке в каждом варианте.
- **Новая роль qa_impact_analyst (H5) — рабочий промпт в agents/qa_impact_analyst_agent.md:** вердикты keep/revalidate/retire по каждому затронутому тесту; revalidate = тест исключается из релизного прогона, требование обновления уходит в чеклист; сомнение → безопасный дефолт revalidate; счет вердиктов сверять программно. Первый прогон (R2): 102/7/0, все revalidate — web-сьют, эскалации в sdd отдельным списком с адресатом.

**Branch protection действует и против ПМ (GH013):** после approve ревьюера локальный merge feature-ветки в main проходит, но push origin/main отклоняется («Changes must be made through a pull request») — ожидаемое состояние, не ошибка; локальный main опережает origin на коммиты до мержа PR. Завершение цикла: merge PR через `gh pr merge <NN> --merge` (gh auth настроен) или в UI Заказчиком. Не пытаться обходить замок force-push/переконфигурацией. Если замок мешает, Заказчик отключает/смягчает ruleset в UI: Settings → Rules → Rulesets → правило → Disabled или снять «Require a pull request»; случай «был не в той репе» — список rulesets виден без авторизации через `GET api.github.com/repos/<owner>/<repo>/rulesets`. Probe-команды на защищенном репо (push, reset --hard) требуют approval — не злоупотреблять. Ревьюер коммитит review-файл в feature-ветку поверх фикса — при merge ветки review-файл доезжает до main сам, отдельного переноса не нужно.

Роутинг ревью по типу диффа (таблица в AGENTS.md): код продукта → code_reviewer; автотесты tests/** → qa_case_reviewer (оси G8: ассерты дословны кейсу, изоляция, детерминированность sleep=0, селекторы, TC-ID); кейсы/чеклисты → qa_case_reviewer; спеки/sdd → ПМ + валидация; пайплайн scripts/flow.yml → code_reviewer (G7: DevOps-агент нет).

Branch protection — состояние ЗАМКА проверять на живом репо перед тем, как полагаться на «PR единственный путь»: `gh api repos/<owner>/<repo>/branches/main/protection` (404 = замок выключен). Ruleset, отключенный ради одного срочного цикла, остается выключенным МОЛЧА — «PR — единственный путь» незаметно деградирует в дисциплину; повторное включение замка — обязательный трек-шаг закрытия того цикла, не опция. Проверка фактом: пустой commit + push в main должен отклониться rules violation. Probe-команды на защищенном репо (push, reset --hard) требуют approval — не злоупотреблять.

G9-типизация артефактов: итоговые (approved-кейсы, reviews/, спеки, тесты, product-overview) живут в main постоянно — это аудит-след, правило 7; промежуточные (одноразовые смоки, черновики, new-дубли) создаются в feature-ветке и удаляются релизной чисткой (шаг «свернуть промежуточные» после зеленого регресса RC, до мержа в main). Первый запуск чистки: 10 smoke-скриптов backend/ + test-model/new дубль.

## QA-контур (первый прогон — уроки)

- **Одна QA-роль = одна делегация; весь контур одним сабагентом — запрещено (указание Заказчика: «я специально 5 ролей делал, чтобы контекст не переполнять»):** слитый в одного сабагента цикл (impact → чеклист → кейсы → ревью → автотесты) дает (а) контекст, раздутый всеми пятью этапами к концу цикла — класс деградации E16, (б) qa_case_reviewer, ревьюящий кейсы, написанные его же контекстом минуту назад — независимость автора/ревьюера мертва, (в) плату за раздутый контекст × 5 этапов. Передача между ролями — только артефактами в test-model/; исключение — мелкие пакеты (<5 CHK) MAY объединять impact+checklist. Если запущенного «циклового» сабагента надо сузить — steer с новой границей мандата («выполни только этапы X и Y, ревью и автоматизация — другими делегациями») + коммит готовых артефактов до остановки.

- **DS-эскалации QA-аналитика:** нетестируемые/неспецифицированные места спеки фиксировать списком DS-N в разделе «Дефекты спеки» чеклиста (описание + эскалация ПМ); CHK под DS помечать в строке «Отложен: DS-N» и кейс НЕ создавать — ревьюер подтверждает правомерность отложения, это не непокрытие. DS-список передавать Заказчику одним пакетом после этапа кейсов.
- **DS-режим кейса:** для неспецифицированного поведения ожидание = «фактический результат, не 5xx, таблица/данные целы», а семантика — в протокол для эскалации; трактовка ПМ (DS-кейсы фиксируют факт) доводится до ревьюера в brief, иначе он потребует уточнения ожиданий до решения DS.
- **Порядок шагов кейса = зависимости операций:** проверяя календарные/статусные инварианты через API, следить, чтобы промежуточная операция (move в done перезаписывает done_at текущим моментом) не перезаписывала поле, смещаемое следующим шагом, — UPDATE до move теряет смысл, кейс дает ложный дефект или нефиксируем; ревьюер ловит именно инверсию порядка.
- QA-задачи в tasks.md change-пакета отсутствуют (нумерация только разработки) — QA-контур трекается через PLAN.md, чекбоксы не отмечаются.
- **Итерации кейс-ревью сужаются — держи диф узким:** доработка после return правит ТОЛЬКО отмеченные кейсы; повторное ревью = только диф + регрессия ранее устраненных замечаний. Инверсия порядка шагов при «исправлении» сама создает новый major (ревью-002 поймал именно это) — автору передавать рекомендацию ревьюера дословно, не пересказом.
- **Валидация автотестов ПМ — сначала подгонка среды, потом вердикт:** перед прогоном прочитай `tests/api/conftest.py` (ожидаемый base_url/порт, фикстуры кредов) и тестовые пароли из approved-кейсов; сьют падает лесом ошибок (десятки ERROR на фикстурах), если сервер слушает не тот порт или БД засеяна чужими паролями — это среда, не дефект сьюта. Эталон: свежая БД, seed ровно теми паролями, что в кейсах, сервер на порту из conftest, затем `pytest -q`.
- **Дизайн автотест-сьюта, проверенный на пилоте:** деградация в skip без env-пути к БД (сьют остается запускаемым без подъемa сервера БД-кейсов); НФТ-процедуры (рестарт, нагрузка) — `@pytest.mark.manual` с обоснованием в tests/README, не кривая автоматизация; TC-ID кейса — в docstring каждого теста, трассировка кейс→тест — таблицей в README; Secure-кука требует https-базы или trustworthy-localhost-обертки в conftest (requests молча не шлет Secure-куки по http).
- **Регрессионное правило конвейера (решение Заказчика, стоит в спеке regression):** после архивации change его сьют — регрессионный набор; каждый следующий change подтверждается полным зеленым прогоном tests/ до архивации своего пакета, новые approved-кейсы пополняют набор. Требование заказчика «автотесты станут регрессионными» оформлять СА-дельтой (отдельный домен regression), не договорностью в чате — иначе правило не доживет до следующего релиза.
- **E2E-трек — отдельная ветвь QA-контура:** чеклист с нумерацией CHK-E-N (E = E2E, отличать от API-чеклиста), пункты — сквозные бизнес-сценарии через несколько доменов (источник — master-specs), НЕ дублирующие API-сьют: только то, что требует браузерного контекста (DOM, модалки, редиректы, подсветка). Найденные на проде UI-дефекты включать как regression-пункты чеклиста. Полный цикл тот же: чеклист → кейсы → ревью → автотесты — трассируемость полная, «скриптом мимо конвейера» не писать.
- **Playwright-кейсы: селекторы только рольные/семантические** (get_by_role/label/text, data-* как test-id-контракт), class/XPath/sleep — 0; ID-локаторы допустимы только для скрытых элементов без ARIA-роли (обоснование — в шапке файла кейсов). Ревьюер сверяет селекторы с реальной разметкой и JS-кодом (клик-обработчики существуют) — наблюдение «тест вскроет продуктовый дефект» фиксировать до прогона, тест писать как есть: падение = баг-репорт, код теста не подгонять.
- **Формирование регресса (G5, архитектура Заказчика):** два процесса — предрелизный прогон `pytest tests/` целиком как отдельный этап пайплайна; пост-релизное пополнение через метки и аналитика. Метку `# regression: keep|candidate-archive` + обоснование ставит qa_automation ПРИ написании теста (создатель знает его смысл); пост-релизный qa_regression_analyst (новая роль, внедрить после первого релиза) читает только метки+спеку — не код — и пишет манифест `test-model/regression/manifest.md` (тест → keep/archive + причина); archive-тесты переносятся в tests/archive/ и не гоняются. Скрипт-манифест и автоматический выбор «устойчивое vs разовое» отклонены: это семантическое решение, скрипту не доверить.
- **Impact-анализ регресса при изменении спеки (H5, роль qa_impact_analyst):** при MODIFIED/REMOVED дельтах часть существующих тестов устаревает; постфактум при фейле = ложный пожар на релизном прогоне. Запуск после СА, до кейсов (чеклисты упразднены — J23); вход — дельты + манифест + трассировка TC↔Requirement; выход — `test-model/impact/<change-id>.md` с вердиктом по каждому затронутому тесту: keep / revalidate (pending_update, исключен из прогона, кейс обновляется) / retire (в архив). Требования «обновить кейс X» идут в чеклист. Промпт создается при первом change с MODIFIED-дельтами; сверку Requirement↔TC по файлам можно вынести в flow_check.
- **Новая работа между ролями = отдельная роль, не приклейка к существующей:** при появлении промежуточной работы (impact-анализ между СА и кейсами) пользователь явно проверяет чистоту границ ролей — «у новой работы же вход и выход другие, не запутаем?» — и отклоняет приклейку ради экономии. Вопрос при проектировании: у новой работы свой вход/выход и своя зона? Тогда роль (по линзе), а не расширение чужого промпта.
- **G3/G7 правила ревьюера:** поведение, уже покрытое регресс-набором tests/, проверять прогоном сьюта (`pytest -k`), свои смоки — только для нового поведения; при ревью по PR-диффу — сначала регресс-прогон, свои скрипты только на разницу. Изменения пайплайна конвейера (flow_check, flow.yml, scripts/) — зона dev на общих основаниях. Прежний отказ от DevOps-агента (G7) Заказчик отменил после болей ручных раскаток: devops_agent (инфра, деплой-скрипты, runbook окружений, зона deploy/** + ops/**) записан в BACKLOG фабрики — до формализации промпта деплой-артефакты готовит и ревьюит ПМ по правилам раздела питфоллов ниже.
- **H4 (решение): линтеры вместо Sonar** — Sonar перебор на ~1.2К строк; ruff (Python) + eslint (JS) по одной строке в flow.yml: гоняются только в CI/локально, в контекст агентов не попадают. Порог усложнения до Sonar: >10К строк или командная разработка.
- **Тюнинг QA-агентов на деградацию (блок H, применить со следующего QA-цикла):** 1 кейс = 1 файл (`new/<change-id>/TC-<domain>-NNN.md`) — ревьюер грузит кейс поштучно: прочитал → сверил → записал замечание append-only в review-файл → выгрузил из контекста → следующий; партии >10–12 кейсов ревьюить по частям (approve всех партий = approve пакета). Причина: ревью одного большого файла 18 кейсов заняло вдвое дольше нормы из-за роста контекста.
- **E2E-сьют падает на сборе вместе с API-сьютом — конфликт опций pytest:** pytest-playwright транзитивно тянет pytest-base-url, который регистрирует опцию `--base-url`; собственная опция с тем же именем в conftest API-сьюта дает «дублирующаяся опция» на сборе ВСЕГО pytest. Решение: базовый URL только через env (EKOTOV_WIKI_BASE_URL), собственные argparse-опции в conftest не добавлять при смешанном стейте. Зависимости web-сьюта (playwright + pytest-playwright + `playwright install chromium`) пре-установить в venv до делегирования автоматизатора — как TestClient/bcrypt, это пре-флайт ПМ.
- **Новые ID-форматы артефактов проверять на совместимость с регэкспами ворот:** flow_check матчит трассировку `TC-[a-z0-9]+-\d{3}` и файлы багов `^BUG-\d{3}` — camelCase `TC-UI-001` не матчился (тесты признавались «без трассировки»), `BUG-1` (одна цифра) не матчился. При заведении нового префикса ID (CHK-E-N, TC-UI) прогонять flow_check ДО коммита; расширять регэкспы ворот (`[a-zA-Z0-9]`, требование ровно 3 цифр) в той же сессии, что и новый формат.
- **Сабагент уперся в лимит итераций (TRUNCATED, ~250 вызовов/79 мин) — хвост доделывает ПМ, не перезапуск:** работа была почти закончена (файлы созданы, прогон выполнен), но без коммита и без контрольного прогона соседнего сьюта после конфиг-фикса. Порядок приемки: прочитать «Незакрытое» из отчета → выполнить контрольные прогоны самому → закоммитить самому → реестр сессий почистить. Деградации не было (здесь это лимит, не делериум) — переигрывать с нуля дорого и бессмысленно.
- **Уточнение Заказчика — сначала переформулируй и предложи вариант, не действуй по первой интерпретации:** поправки типа «я имел в виду не X, а Y» и «нет» без пояснений означают «остановись и уточни одним clarify-вопросом с вариантами» — два подряд неверно понятых уточнения стоили цикла доработок впустую. После подтверждения — работай дальше без повторных вопросов. директива «сворачивайся» может быть отменена Заказчиком («пусть продолжает») — отменять свою steer-директиву новой немедленно, не позволять сабагенту свернуть начатую работу из-за устаревшей директивы.
- **Playwright-зависимости не входят в requirements самого продукта по умолчанию:** для web-сьюта нужны playwright + pytest-playwright + `playwright install chromium` — пре-флайт ПМ перед делегированием; без них сбор даже не стартует (ImportError pytest_playwright).
- **API-сьют требует внешнего сервера (env EKOTOV_WIKI_BASE_URL, дефолт localhost:8080), web-сьют поднимает свой стенд сам:** контрольный прогон API-сьюта после конфиг-фиксов — поднять сервер с засеянной БД паролями кейсов, прогнать, остановить; «82 errors на фикстурах connection refused» = сервер не поднят, а не дефект.
- **Новый прод-дефект, предсказанный ревьюером кейсов до прогона (BUG-001: клик по карточке из поиска не открывает карточку — renderCard search.js без click-обработчика), тест писать как есть, не подгонять:** падение теста = подтверждение баг-репорта; фикс идет dev-циклом по гитфлоу G6, тест не ослаблять.
- **Дефект, пойманный при автоматизации, помечать xfail(strict), не удалять тест:** тест написан по спеке (ожидание 422), продукт дает 201 — тест остается в сьюте с `@pytest.mark.xfail(strict=True)`; при фиксе продукта он даст XPASS и сорвет прогон, принудительно заставив снять метку и превратить в обычный тест — после фикса тест доказывает, что баг закрыт (BUG-002: TC-fast2-004, снятие xfail = часть коммита фикса). Баг-репорт оформлять сразу с кейсом, окружением и ожиданием/фактом.
- **Фикс-ветка, построенная на еще не влитой QA-ветке (cherry-pick тестового коммита): вливать исходную QA-ветку в main ПЕРВОЙ**, затем фикса — дубликат cherry-picked коммита git переживает без конфликтов (содержимое идентично), обратный порядок дает тот же результат, но историю труднее читать. Фикс-дифф для ревьюера давать как `git diff <qa-ветка>..<фикс-ветка>`, не `main..` — иначе ревьюер получит тесты вместе с фиксом.

## Ритм прохода бэклога: после каждого тикета — сразу следующий пункт на обсуждение

Заказчик поправил дважды: (1) не спрашивать разрешения на переход к следующему пункту; (2) «после каждого тикета обсуждай со мной сразу следующий». Итоговый ритм: закончил тикет (правки + [x] + коммит с хешем + счетчик в докладе «N открытых / M закрыто») → СРАЗУ выносишь следующий пункт: проблема → предлагаемое изменение → цена/риск → вопрос «вносим?». НЕ пролетать пачкой и НЕ ждать команды на переход. Для «мне все равно» — решать самому со сверкой индустриальных практик (web_search: RACI, decision log, delegation vs escalation; источники в бэклог). Перед формализацией оценивать реальную важность: правило де-факто соблюдается → закрывать «сделано де-факто + условие возврата», не вносить бюрократию.

## Валидация: скриптами, не агентами (решение Заказчика)

Где проверка автоматизируема — выносить в скрипт (flow_check ворота, check_auth_timing.py AST-анализ), не в пункт чеклиста агента: скрипт дешевле, детерминированнее, не теряется между сессиями. Новый скрипт валидировать в обе стороны: зеленый реальный проект — PASS, сломанный fixture — ожидаемые нарушения. Контекст Заказчика дорог — не раздувать: решения инкорпорировать в as-is описание (мастер-док), журналы не вести; статусы — в существующий PLAN.md, не новый файл; линтеры (ruff/eslint) — в CI, не в контекст агентов.

## Артефакты оркестрации, введенные проходом бэклога

- **`scripts/factory_init.py` (E15) — развертывание конвейера на проект одной командой** (`--target <git-repo> --name [--force]`): каталоги + файлы ворот (flow_check, pr_validate, codegraph, smoke_static, session_archive, session_worktree) + CI + контракты + шаблоны + CONSTITUTION.md из шаблона + проверка среды + post-init ворота (flow_check пустого проекта = OK). Идемпотентен: без --force ничего не перезаписывает. ## Принципы прохода бэклога (решения Заказчика)

- **Главный критерий — экономия контекста и простота:** не заводить новый файл/механизм, если существующий покрывает (статус — в PLAN.md, не новый файл); при предложении механизма думать, не раздует ли он контекст сабагентов и сможет ли Заказчик разобраться без ПМ.
- **Где можно проверить скриптами — проверяем скриптами, не агентами:** вынесенная в скрипт проверка (AST-анализ, структурные ворота flow_check) дешевле, детерминированнее и не теряется между сессиями; пункт чеклиста агента «проверь X» создавать только когда проверка по природе человеческая (качество формулировок, смысловая трассировка). Прецедент: timing-safety аутентификации — `scripts/check_auth_timing.py` (AST: нет `==` на секретах, checkpw, dummy-хеш, токены через secrets). Новый проверочный скрипт валидировать в обе стороны: зеленый реальный проект — PASS, сломанный fixture — ожидаемые нарушения.
- **Перед формализацией — анализ реальной важности:** если правило де-факто соблюдается (например, эскалации всегда шли через спеку, никто не правил напрямую), чеклист-бюрократия не вносится; пункт закрывается «сделано де-факто + условие возврата» (признак: эскалации теряются / то же решается повторно).
- Заказчик хочет структурированный контекст (блоки, выборочное чтение), а не журналы решений: решения инкорпорировать в as-is описание, историю держать в git/answers.
- Каждое процессное решение рассматривать через опцию «выделить сабагента». Критерии заведения роли: повторяемость, изоляция контекста, собственная зона записи, экономика токенов. Не проходит — правило/скрипт/расширение существующей роли (прецедент отказа, впоследствии ОТМЕНЕННЫЙ Заказчиком: DevOps-роль — отказ пересмотрен после двух падений подряд деплой-скрипта, отловленных руками Заказчика, а не конвейером; вывод: критерий повторяемости у деплоя выполнялся изначально, отказ экономил токены ценой слепой зоны).

## Питфоллы

- **Удаление веток после релиза — только через `-d` после проверки `git rev-list --count main..<branch>` = 0:** хвосты релиза (feature-ветки, worktree в /tmp, test/*) чистить пакетом по завершении релиза, не «когда накопится» (после R2 висели 4 worktree + 11 веток). Ветки с уникальными коммитами (потребуют force-delete) — только после явного ОК Заказчика.

- **Зачистка worktree — сначала `git status --short` и проверка коммитов, потом `session_worktree.sh remove`:** untracked-артефакты (review-файл повторного ревью, отчеты) умирают вместе с деревом — закоммиченное переживает merge, незакоммиченное переживает только до remove. В ТЗ ревьюеру, работающему в worktree, явно требовать ЗАКОММИТИТЬ review-файл в ветку, а не «запиши файл»; перед remove — дерево чисто и все заявленные артефакты видны в git. Потерянный вердикт = повторная делегация ревьюера с нуля; восстановление «по памяти из отчета» недопустимо (не артефакт).

- Долгосрочный план вести в `PLAN.md` репозитория — `todo_list` обнуляется при смене модели/перезапуске сессии; git — единственное надёжное хранилище. После потери сверяться с PLAN.md, не восстанавливать по памяти.
- Git-команды давать как `git -C /home/openclaw/<repo> ...` — cwd терминала дрейфует после `cd` в цепочках команд, относительные пути молча ломаются.
- Документацию с GitHub тянуть `curl -sL https://raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>` (список файлов — `api.github.com/repos/<owner>/<repo>/contents/<dir>`): web_extract в этой среде сидит на search-only бэкенде и страницы не извлекает, browser_exec блокируется Cloudflare; raw-эндпоинт отдает чистый текст без bot-wall. Большой док — скачать один раз в переменную и резать диапазоны в Python, не перекачивать.

Стоящее правило Заказчика: при «мне все равно» ПМ решает сам, НО сверяется с популярными индустриальными практиками через web_search и фиксирует источники в пункте бэклога/контракте — решение без опоры на практику не принимать молча.

То же — к СОБСТВЕННЫМ деплой-скриптам: вызовы `python -m app.*` оборачивать в подшелл с cwd родителя пакета — `(cd "$APP_DIR/backend" && sudo -u <юзер> .venv/bin/python -m app.migrate_categories)`; скрипт, запущенный из произвольного каталога, падает с ModuleNotFoundError, и этот файл видит Заказчик, а не автор (падение воспроизводилось дважды на разных машинах вызывающего).

- **В goal повторного ревью передавай ТОЛЬКО диф-границу фикса («проверяется только диф, не вся задача заново») + ожидание по каждому finding — повторное ревью всей задачи удваивает стоимость без прироста. Minor findings при approve: точечный фикс-цикл (dev чинит все миноры одним коммитом в той же ветке → повторное ревью по границе) дешевле приемки как есть; мажоры/блокеры — return по общим правилам. Редакционные замечания ревьюера к чужому пакету (неверное утверждение, пропущенный бамп, лишний [P]-маркер, ссылка на старую версию) ПМ вносит сам точечным патчем сразу при приемке ревью — возврат автору ради опечатки дороже фикса; содержательные (смена решения) — автору.

- **Перед спавном параллельных dev-сабагентов создать worktrees ПМ-ом самим** (по одному на сессию, путь в goal), не доверять сабагенту — сессии стартуют одновременно, и каждая пыталась бы создать ветку от одного HEAD; у каждой параллельной задачи своя ветка feature/r3-<задача>, созданная ДО старта сессий.
- **Утверждение Заказчиком варианта/пресета вносить СРАЗУ в оба артефакта — requirements (история статусов) И tasks.md соответствующей задачи** (точный состав: что именно выбрано, где мокап) — выбор, зафиксированный только в чате, теряется между циклами; заодно чистить устаревшие блоки статуса (ЧЕРНОВИК после УТВЕРЖДЕНО — противоречие в одном документе).
- **Скриптовые питфоллы execute_code: Python heredoc-строки внутри subprocess.run дают SyntaxError на тройных кавычках/EOF-маркере** — правки файлов делать прямым I/O (`open(...).write()`) или patch-инструментом; при ошибках UnicodeDecodeError в subprocess — передавать `encoding='utf-8', errors='replace'` явно (кириллица в grep-выводе).
- SMOKE-FAIL может быть багом тестового скрипта, не продукта — перепроверь expectations перед вердиктом: 307 на trailing slash, 405 на несуществующем GET-маршруте, неверный литерал 422-тела — типичные ложные FAIL (ловились дважды за сессию на независимых скриптах). Каждая FAIL-строка смоука либо подтверждается корректным запросом, либо чинится в скрипте; в отчет помечается «дефектов кода нет».
- Перед спавном dev/ревьюера, чья задача требует TestClient или seed, предустанови test-зависимости в venv сам (httpx2 для TestClient, bcrypt==5.0.0 для seed) — сабагент без них падает на импорте и цикл диспетчеризации теряется целиком; это повторялось дважды, пока не стало пре-флайтом ПМ.

Правки файлов из execute_code — прямым Python I/O ядра (`open(...).read()/write()`) или patch-инструментом, НЕ subprocess-строкой с heredoc внутри Python-кода: вложенные тройные кавычки и EOF-маркер ломают синтаксис обертки до исполнения (SyntaxError, терялись попытки).

Заявление «защита реализована» без замера не принимается.
- MODIFIED-дельта OpenSpec требует существующего master-spec: для greenfield-пакета при архивации нормализуй заголовки MODIFIED → ADDED в дельтах ДО `openspec archive` (master-spec еще пуст; валидатор отказывает и abort-ит без изменений — слияние просто не произойдет). После успешного archive валидатор --strict падает на tool-сгенерированных Purpose-плейсхолдерах во всех новых master-specs — замени их осмысленными purpose по каждому домену в той же сессии и прогони validate повторно (8/8 passed — критерий завершенности архивации).
- При противоречии формулировки задачи в tasks.md, или собственного brief делегирования ПМ, и sdd — sdd приоритетен (API-контракт — источник правды, tasks.md и brief пишутся раньше и отстают от rN-правок sdd): реализуй/поручай по sdd, расхождение вынеси в отчет для ревьюера. Сверяй свой brief со sdd ДО спавна сабагента — формулировка ПМ не источник правды и ошибаетесь так же, как tasks.md (подтверждалось трижды: текст 401, поле `body` против моего `text`, user_id в общей доске — ревьюер все три раза подтвердил выбор sdd).

- Рекомендации ревьюера, относящиеся к БУДУЩИМ задачам, фиксировать подзаметкой в tasks.md под соответствующей задачей (пример: logout-элемент в 3.1, кастомный 422-handler в 9.1) — устные рекомендации теряются между циклами, подзаметка доезжает до исполнителя.
- При делегировании задач с угадываемыми именами полей (текст комментария, ключи JSON) не формулируй тело из головы — ссылайся на sdd §4 дословно или давай dev свободу сверки: расхождение поле→422 ловится только смоуком (поле `body`, не `text`, подтвердилось на 4.2).
- Гонко-чувствительные инварианты (уникальность/лимиты на конкурентных запросах) в SQLite проверяй через BEGIN IMMEDIATE до SELECT — autocommit-SELECT не составляет транзакцию с INSERT и гонка реально воспроизводится (обе-201 в 11/20 прогонов до фикса); ревьюер обязан воспроизводить гонку сам, «писал по спеке» не доказательство.

- **Ворота, исполняемые в CI, проектировать под shallow-клон и локальные пути:** merge-base ancestry на shallow недоказуема (checkout fetch-depth: 0 или fallback на GitHub API compare), пути worktree машины прогона из артефакта в CI не читаются (→ WARNING, инвариант несет commit-сверка). Локально зеленый прогон ворот ≠ CI-зеленый — симулировать CI-ограничения (clone --depth 1) до коммита.
- **Дженерик-имена review-файлов привязывать к задачам через review-mapping.json, а мету писать вплотную:** имя review-003.md не матчится ни одним регэкспом форматов (нужен NNN-сегмент или задача-сегмент) — покрытие задач дает `code-reviews/<change>/review-mapping.json` (файл → список task-ID). Мета J10 парсится регэкспом «Reviewer-Delegation, затем ≤6 не-алнум. символов, deleg_<id>» — текст между «Reviewer-Delegation» и deleg_<id> (даже «- review-003: …») рвет матч, и approve считается не покрытым. flow_check при непокрытии печатает точную задачу и причину — править формат меты, не ослаблять ворота.
- **pkill/pgrep -f паттерном гасит собственную команду:** паттерн матчится на аргументы собственного шелла (self-SIGTERM посреди цепочки). Символьный класс (foo_ap[p].db) или pgrep + kill по явным PID.
- **Перед коммитом на ветке — `git branch --show-current`:** после любых «checkout main && reset --hard origin/main» в цепочке следующие коммиты молча ложатся на main, а пуш именованной ветки становится no-op (дважды за релиз: баг-репорты уезжали на main, CI не перезапускался). Возврат — cherry-pick sha из reflog main; правильный порядок: checkout ветки → коммит → push.
- **regress-final исполняет выделенный regress_runner с узким брифом** (ветка/коммит/сьюты; контекст релиза не нужен), не ПМ: изолированный worktree --detach, `flowctl regress --change <id> --final --timeout 1800` (дефолтный таймаут 120s дает фиктивный «PASS по таймауту»), FAIL → изолированный перепрогон 2× (баг vs флак), артефакт [chore] в ветку. Tooling/зеркала заморозить ДО прогона: любой коммит скриптов после артефакта = перегон по свежести. **Решение Заказчика (эшелоны): полный regress — пакетно перед плановым деплоем, НЕ на каждый change; на каждый change — smoke + доменный regress своего куска; параллелизация `pytest -n auto` (xdist) с isolating-фикстурами и serial-fallback; pytest-xdist — в пре-флайт тест-окружений проектов.**
- **Контракты — в промпты ролей, не в голову ПМ (корневой вывод разбора кругов CI):** стоячие требования (репорт BUG-NNN = часть коммита фикса; ветка/worktree из ALLOW; формат review-файла; freeze tooling) вшиваются в системные промпты ролей, а не пересказываются в тексте делегации — пересказ теряет куски, и каждый потерянный кусок = круг CI. При заведении новой роли/делегации сверять: какой standing-контракт нужен этой роли и есть ли он в её промпте.
